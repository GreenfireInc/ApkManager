## Short answer

The APK only contains native libraries for **ARM**: 40 files under `lib/arm64-v8a/` and 41 under `lib/armeabi-v7a/`, with **no `lib/x86_64/`** at all. The "universal" in the filename is misleading. ATL runs Android code natively on the host CPU, with no instruction-set emulation, so on an x86_64 PC it only looks in the (missing) x86_64 folder. The game's `Application` class loads its anti-cheat library `libanogs.so` first, the lookup fails, and the process aborts.

```text
JNI DETECTED ERROR IN APPLICATION: JNI FindClass called with pending exception java.lang.UnsatisfiedLinkError:
  dalvik.system.PathClassLoader[DexPathList[[zip file ".../ghax.jar", zip file "~/Applications/android/com.tencent.ig.from.disk.universal.apk"],
  nativeLibraryDirectories=[.../android_translation_layer/natives, ~/.local/share/android_translation_layer/com.tencent.ig.from.disk.universal.apk_/lib, ...]]]
  couldn't find "libanogs.so"
```

The class loader searched ATL's own `natives/` folder and the app's extracted library folder (`…apk_/lib`), and ATL had extracted nothing for x86_64 because the APK has none.

## Why it happens

```bash
$ unzip -l com.tencent.ig.from.disk.universal.apk 'lib/*' | awk '{print $4}' | cut -d/ -f2 | sort | uniq -c
     40 arm64-v8a
     41 armeabi-v7a
```

- Android ARM libraries contain ARM machine code. An x86_64 CPU can't execute it.
- Phones and Android emulators that run ARM games on x86 use binary translation (Intel's Houdini, Google's libndk_translation, or Lepton's `install-arm-translation.sh`). ATL has no such layer. It loads `.so` files straight into its own x86_64 process through bionic_translation.
- PUBG's start-up code loads `libanogs.so` (Tencent ACE anti-cheat) before anything else, so that's the first missing library reported. The game engine (`libUE4.so`) and everything else are ARM-only too.

Even on an ARM64 Linux machine, where the libraries would match, this game would be blocked by its anti-cheat, which detects non-standard Android environments, and by its need for Google Play services and a full GPU stack.

## Suggested fixes

There is **no runtime code fix that makes this APK run in ATL on x86_64.** Options:

- **Use a runtime with ARM translation.** Waydroid with `libndk_translation` or `libhoudini` (for example via the `waydroid_script` helper), or Lepton with its ARM translation installed. Tencent's anti-cheat may still refuse to run.
- **Get an x86_64 build.** PUBG MOBILE doesn't publish one, so not an option here.

### Make the failure clear (ATL)

In ATL's APK loading (`ATLLoadedApp` / native library extraction), check the ABIs before starting the app:

```java
// android/atl/ATLLoadedApp.java (sketch)
private static String hostAbi() {
	return Build.SUPPORTED_ABIS[0];   // "x86_64" on this machine
}

private void checkAbi(ZipFile apk) {
	boolean hasAnyLib = false, hasHostLib = false;
	for (Enumeration<? extends ZipEntry> e = apk.entries(); e.hasMoreElements();) {
		String name = e.nextElement().getName();
		if (name.startsWith("lib/") && name.endsWith(".so")) {
			hasAnyLib = true;
			if (name.startsWith("lib/" + hostAbi() + "/"))
				hasHostLib = true;
		}
	}
	if (hasAnyLib && !hasHostLib) {
		Slog.e(TAG, "This APK has native code only for other CPU architectures; "
		          + "it can't run on " + hostAbi() + " without an ARM translation layer.");
		// show a GTK dialog with that message and exit(1) instead of crashing
	}
}
```

### Warn before launch (ApkManager)

ApkManager already opens the APK to read its manifest and icon. It could list the `lib/<abi>/` folders and, if there are native libraries but none for the host's architecture (`uname -m`: `x86_64` → `x86_64`, `aarch64` → `arm64-v8a`), show a warning in **Properties** and before **Run**: "This app only includes ARM code and can't run in Android Translation Layer on this PC." That covers this finding and the TikTok one, and would explain the Wine x86 (32-bit) one too.
