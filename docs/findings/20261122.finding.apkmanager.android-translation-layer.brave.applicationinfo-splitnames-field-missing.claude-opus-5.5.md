## Short answer

Brave is built on Chromium, which checks for installed app-bundle splits while the `Application` object is being attached, before any activity starts. It reads the public field `ApplicationInfo.splitNames`, which Android has had since API 26. ATL's `ApplicationInfo` doesn't declare that field, so ART throws `NoSuchFieldError` and the process aborts.

- `NoSuchFieldError … splitNames … [Ljava/lang/String;`: compiled code reads the field `String[] splitNames`, and the class ATL supplies doesn't have it.
- It happens in `SplitChromeApplication.attachBaseContext`, the first app code that runs.
- The CheckJNI abort is secondary. ATL's native launcher makes another JNI call (`FindClass`) with the exception still pending.

## Why it happens

Chrome and Brave ship as Android App Bundles. The Play Store and Aptoide may install them as a base APK plus "split" APKs, and Chromium's `BundleUtils` checks which splits are present:

```java
// Chromium BundleUtils (simplified)
public static boolean hasAnyInstalledSplits() {
	ApplicationInfo info = ContextUtils.getApplicationContext().getApplicationInfo();
	return info.splitNames != null && info.splitNames.length > 0;
}
```

ATL's `ApplicationInfo` follows an older Android release. It has `splitSourceDirs` but not `splitNames`, which was added in API 26.

---

## Suggested fix in the runtime (ATL)

`src/api-impl/android/content/pm/ApplicationInfo.java`, next to `splitSourceDirs`:

```java
	public String[] splitSourceDirs;

	/**
	 * The names of all installed split APKs, ordered lexicographically.
	 * ATL loads a single APK, so this stays null (no splits).
	 */
	public String[] splitNames;

	public String[] splitPublicSourceDirs;
```

`null` is correct for ATL, which runs a single APK. Chromium treats `null` as "no splits" and continues with the base APK.

If ATL ever supports split installs (several APKs at once), fill `splitNames`, `splitSourceDirs` and `splitPublicSourceDirs` in the code that builds `ApplicationInfo` from the parsed package. The parser already has `PackageInfo.splitNames`.

---

## What to expect after the fix

This removes the first blocker only. Chromium-based browsers need several things ATL doesn't provide today:

- **Separate sandboxed processes:** renderer and GPU processes started as `isolatedProcess` services.
- **Mojo IPC over binder-like channels.**
- **A `SurfaceView`/`SurfaceControl` compositor path.**

Expect a different crash further into startup. For a browser, a Linux build of Brave, or Waydroid, is the realistic route.
