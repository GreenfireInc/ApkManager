## Short answer

There are two separate failures:

1. **`NoSuchMethodError: incrementProgressBy(I)V`** on the UI thread. Wine shows an "Extracting files..." progress dialog and bumps it once per file. ATL's `ProgressDialog` has no `incrementProgressBy`. CheckJNI reports the error and dumps the threads, but the extraction thread keeps going and unpacks Wine into `files/x86/`.
2. **`NullPointerException` in `get_so_dir()`**, which ends the run with `System.exit(10)`. ATL reports `SDK_INT = 17` (Wine's minSdk), so Wine uses the pre-Lollipop `Build.CPU_ABI` (`x86_64`) instead of `Build.SUPPORTED_ABIS`. It looks for `files/x86_64/bin/wineserver`, but this APK only ships **32-bit x86**, so it finds nothing, `get_wine_abi()` returns `null`, and `abi.equals("x86")` throws.

Fixing the ABI lookup would only move the failure: ATL is a 64-bit process and can't load Wine's 32-bit `i386-unix/ntdll.so`.

## Why it happens

### 1. The progress dialog

```java
// WineActivity.copyAssetFiles (wine-7.0)
createProgressDialog( copy_files.size(), "Extracting files..." );
for (String name : copy_files)
{
    copyAssetFile( name );
    runOnUiThread( new Runnable() { public void run() {
        progress_dialog.incrementProgressBy( 1 ); }});   // line 321: not in ATL
}
```

### 2. The ABI lookup

```java
// WineActivity (wine-7.0)
private String[] get_supported_abis()
{
    if (Build.VERSION.SDK_INT >= 21) return Build.SUPPORTED_ABIS;
    return new String[]{ Build.CPU_ABI };          // ATL: SDK_INT = 17, so { "x86_64" }
}

private String get_wine_abi()
{
    for (String abi : get_supported_abis())
    {
        File server = new File( getFilesDir(), abi + "/bin/wineserver" );   // files/x86_64/bin/wineserver: missing
        if (server.canExecute()) return abi;
    }
    Log.e( LOGTAG, "could not find a supported ABI" );
    return null;
}

private String get_so_dir( String abi )
{
    if (abi.equals( "x86" )) return "/i386-unix";  // line 102: NullPointerException
    ...
}
```

What the APK contains:

```text
lib/x86/*.so           (libcups, libfreetype, libgnutls, …)   32-bit x86
assets/x86/…           1,056 files (wineserver, wine, i386-unix/*.so, i386-windows/*.dll)
```

After the run, `files/x86/bin/wineserver` exists and is executable, so the extraction itself worked. Only the ABI choice failed.

On a real 64-bit Android device, the installer sees a 32-bit-only APK and runs the app as a **32-bit process**, so `CPU_ABI` is `x86` and everything lines up. ATL has no 32-bit mode: its ART, bionic_translation and GTK stack are all x86_64.

## Suggested fixes in the runtime (ATL)

### 1. Implement `ProgressDialog`'s progress methods

`src/api-impl/android/app/ProgressDialog.java`. Keep the numbers so apps that read them back behave:

```java
public class ProgressDialog extends AlertDialog {
	public static final int STYLE_SPINNER = 0;
	public static final int STYLE_HORIZONTAL = 1;

	private int progress;
	private int secondaryProgress;
	private int max = 100;
	private boolean indeterminate;

	public ProgressDialog(Context context) {
		super(context, 0);
	}

	public ProgressDialog(Context context, int themeResId) {
		super(context, themeResId);
	}

	public void setIndeterminate(boolean indeterminate) { this.indeterminate = indeterminate; }
	public boolean isIndeterminate() { return indeterminate; }

	public void setProgressStyle(int style) {}

	public void setProgress(int progress) { this.progress = Math.max(0, Math.min(progress, max)); }
	public int getProgress() { return progress; }

	public void setSecondaryProgress(int secondaryProgress) { this.secondaryProgress = secondaryProgress; }
	public int getSecondaryProgress() { return secondaryProgress; }

	public void setMax(int max) { this.max = max; }
	public int getMax() { return max; }

	public void incrementProgressBy(int diff) { setProgress(progress + diff); }
	public void incrementSecondaryProgressBy(int diff) { setSecondaryProgress(secondaryProgress + diff); }

	public void setProgressNumberFormat(String format) {}
	public void setProgressPercentFormat(java.text.NumberFormat format) {}

	// existing static show(...) overloads unchanged
}
```

When ATL's `AlertDialog` gains a GTK progress bar, `setProgress` can drive it. Until then the dialog shows its message and the app's bookkeeping works.

### 2. Stop advertising a 32-bit ABI that ATL can't run

`SystemProperties` claims `x86` (`cpu.abi2`, `abilist`, `abilist32`) on x86_64 hosts, but ATL can't load 32-bit libraries. That doesn't cause this crash, since Wine took the `CPU_ABI` path, but it's wrong for apps that pick native code from `SUPPORTED_ABIS`:

```java
		if (System.getProperty("os.arch").equals("x86_64")) {
			properties.put("ro.product.cpu.abi", "x86_64");
			properties.put("ro.product.cpu.abi2", "");
			properties.put("ro.product.cpu.abilist", "x86_64");
			properties.put("ro.product.cpu.abilist64", "x86_64");
			properties.put("ro.product.cpu.abilist32", "");
		}
```

### 3. Warn before launch

As with the PUBG MOBILE and TikTok findings, ATL (or ApkManager) can check the APK before starting it. Here, `lib/x86/` and `assets/x86/` with no `x86_64` counterpart means "32-bit x86 only; this runtime is 64-bit". ApkManager's pre-launch ABI warning (see the PUBG MOBILE finding) covers this case if it treats `x86` as unsupported on x86_64 ATL.

**For actually running Windows programs on this PC,** use the host's Wine directly (`wine program.exe`). The WineHQ repository is already configured on this machine. Wine for Android exists for Android devices; on Linux it adds nothing.
