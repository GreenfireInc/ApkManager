## Short answer

Termux's terminal view measures its font when it's created (`TerminalView.setTextSize` → `new TerminalRenderer(...)`). The renderer calls `Paint.getFontSpacing()`, which has been in Android since API 1. ATL's `Paint` doesn't have it. ART throws `NoSuchMethodError` inside `TermuxActivity.onCreate`, and CheckJNI aborts the process.

## Why it happens

On Android, `getFontSpacing()` is a convenience wrapper:

```java
// AOSP android.graphics.Paint
public float getFontSpacing() {
    return getFontMetrics(null);
}
```

`getFontMetrics(FontMetrics)` returns the recommended line spacing (descent − ascent + leading) and fills in the metrics object if one is given. ATL implements `getFontMetrics` natively but never added the wrapper.

---

## Suggested fix in the runtime (ATL)

`src/api-impl/android/graphics/Paint.java`, next to `getFontMetrics(FontMetrics)`:

```java
	public float getFontSpacing() {
		return getFontMetrics(null);
	}
```

This matches AOSP exactly. ATL's native `native_get_font_metrics` (`android_graphics_Paint.c`, line 186) checks `if (metrics)` before filling in fields and always returns the Pango line height, so passing `null` is safe.

Termux's renderer also sizes its grid from `ascent()` and `measureText("X")`. ATL approximates both: `ascent()` returns `-getTextSize()`, and `measureText` returns 0.6 × text size per character. The terminal grid would be close but not exact. Using real Pango metrics fixes that, along with `descent()` and `getTextScaleX()`, which ATL stubs as `return 0` and which other text-heavy apps call:

```java
	public float ascent() {
		FontMetrics m = new FontMetrics();
		getFontMetrics(m);
		return m.ascent;
	}

	public float descent() {
		FontMetrics m = new FontMetrics();
		getFontMetrics(m);
		return m.descent;
	}

	public /*native*/ float getTextScaleX() { return 1.0f; }
```

`breakText(...)` (always `return 10`) and `setFontFeatureSettings(String)` (empty) are also stubs that text-heavy apps reach.

## What to expect after the fix

The terminal view should appear. Termux itself is still unlikely to work under ATL:

- Its bootstrap environment (shells and packages) is built for the prefix `/data/data/com.termux/files/usr`, which is compiled into every binary. ATL keeps app data in `~/.local/share/android_translation_layer/<apk>_/`, so the bootstrap unpacks to the wrong place and its programs can't find their libraries or configuration.
- The bundled binaries are linked against Android's bionic libc and run as separate processes. bionic_translation only translates libraries loaded *inside* ATL's process, not child programs Termux starts.

For a Linux terminal, the host's own terminal does everything Termux does on Android.
