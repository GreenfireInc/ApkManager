## Short answer

bitchat asks the Bluetooth adapter for its Bluetooth Low Energy (BLE) advertiser in `MainActivity.onCreate`. ATL hands out a `BluetoothAdapter` object, but that class has no `getBluetoothLeAdvertiser()` method. ART throws `NoSuchMethodError`. ATL's native code then calls into Java with that exception still pending, and CheckJNI aborts the process (`SIGABRT`).

## What the error is

```text
at K1.D.<init>(Unknown Source:38)
at K1.d.<init>(Unknown Source:88)
at K1.U.<init>(Unknown Source:105)
at com.bitchat.android.MainActivity.onCreate(Unknown Source:7)

  java.lang.NoSuchMethodError: No virtual method getBluetoothLeAdvertiser()Landroid/bluetooth/le/BluetoothLeAdvertiser;
  in class Landroid/bluetooth/BluetoothAdapter; ... (declaration of 'android.bluetooth.BluetoothAdapter' appears in .../api-impl.jar)
Fatal signal 6 (SIGABRT), code -6 (SI_TKILL)
```

- `NoSuchMethodError`: the app was compiled against Android's real `BluetoothAdapter`, which has had `getBluetoothLeAdvertiser()` since API 21. ATL's version of the class doesn't have it.
- "declaration … appears in …/api-impl.jar" confirms the class came from ATL's Android API implementation, not from the app.
- `JNI DETECTED ERROR … called with pending exception`: the Java exception wasn't caught. Control returned to ATL's native activity-start code, which made another JNI call (`GetMethodID`) while the exception was still pending. With CheckJNI on, ART treats that as fatal and aborts. This abort shows up in most of these crashes; the real cause is always the Java exception named in it.

## Why it happens

ATL implements Bluetooth as a placeholder:

```java
// ATL src/api-impl/android/bluetooth/BluetoothAdapter.java
public class BluetoothAdapter {
	public static BluetoothAdapter getDefaultAdapter() {
		return null;
	}
}
```

```java
// ATL src/api-impl/android/bluetooth/BluetoothManager.java
public class BluetoothManager {
	public BluetoothAdapter getAdapter() {
		return new BluetoothAdapter();
	}
}
```

The two classes disagree. `BluetoothAdapter.getDefaultAdapter()` says "no Bluetooth" by returning `null`, but `BluetoothManager.getAdapter()` returns an adapter object, and calling anything on it fails. bitchat uses the `BluetoothManager` route (the modern one), gets an object, and calls `getBluetoothLeAdvertiser()` on it.

bitchat is a Bluetooth mesh messenger, so BLE is its core feature, and it reaches for BLE straight away.

---

## Suggested fix in the runtime (ATL)

Make the adapter a consistent "Bluetooth is present but switched off" object. Most apps handle that state, because it's what they see on a phone with Bluetooth turned off.

`src/api-impl/android/bluetooth/BluetoothAdapter.java`:

```java
package android.bluetooth;

import android.bluetooth.le.BluetoothLeAdvertiser;
import android.bluetooth.le.BluetoothLeScanner;

public class BluetoothAdapter {
	public static final int STATE_OFF = 10;
	public static final int STATE_ON = 12;
	public static final String ACTION_STATE_CHANGED = "android.bluetooth.adapter.action.STATE_CHANGED";
	public static final String ACTION_REQUEST_ENABLE = "android.bluetooth.adapter.action.REQUEST_ENABLE";
	public static final String EXTRA_STATE = "android.bluetooth.adapter.extra.STATE";

	public static BluetoothAdapter getDefaultAdapter() {
		return null;
	}

	public boolean isEnabled() { return false; }
	public int getState() { return STATE_OFF; }
	public String getName() { return null; }
	public String getAddress() { return "02:00:00:00:00:00"; }

	// Android returns null for both while Bluetooth is off
	public BluetoothLeAdvertiser getBluetoothLeAdvertiser() { return null; }
	public BluetoothLeScanner getBluetoothLeScanner() { return null; }

	public boolean isMultipleAdvertisementSupported() { return false; }
	public boolean isOffloadedFilteringSupported() { return false; }
	public boolean isLe2MPhySupported() { return false; }
}
```

Add empty stubs so the method signatures resolve:

```java
// src/api-impl/android/bluetooth/le/BluetoothLeAdvertiser.java
package android.bluetooth.le;

public final class BluetoothLeAdvertiser {
	private BluetoothLeAdvertiser() {}
}
```

```java
// src/api-impl/android/bluetooth/le/BluetoothLeScanner.java
package android.bluetooth.le;

public final class BluetoothLeScanner {
	private BluetoothLeScanner() {}
	public void startScan(ScanCallback callback) {}
	public void stopScan(ScanCallback callback) {}
}
```

Make sure `PackageManager.hasSystemFeature("android.hardware.bluetooth_le")` stays `false` (it falls into the "not implemented" default today, which returns `false`). That way apps that check the feature first skip BLE entirely.

**Alternative:** make `BluetoothManager.getAdapter()` return `null`, matching `getDefaultAdapter()`. That's what Android does on hardware with no Bluetooth. It's simpler, but more apps dereference the adapter without a null check than call methods on an "off" adapter, so the stub above is the safer default.

### General hardening (helps every "pending exception" crash)

ATL could catch exceptions escaping `Activity.onCreate` and the other lifecycle callbacks in its native start path, log them with a full stack trace (`ExceptionDescribe` / `ExceptionClear`), and close the activity cleanly instead of letting CheckJNI abort on the next JNI call. The app would still fail, but the log would lead with the Java stack trace instead of an ART thread dump.

---

## What to expect after the fix

bitchat should get past `onCreate`. Its mesh networking still won't work, since ATL has no Bluetooth stack, so at best the user interface opens and shows Bluetooth as off. Running it for real needs a full Android environment with Bluetooth passthrough, such as Waydroid.
