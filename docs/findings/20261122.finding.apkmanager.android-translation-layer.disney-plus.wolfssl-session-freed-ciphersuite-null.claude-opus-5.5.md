## Short answer

Disney+ doesn't crash in ATL itself. It **exits with status 10** after its own crash handler (Firebase Crashlytics) catches an uncaught exception on an OkHttp network thread:

```text
java.lang.IllegalStateException: cipherSuite == null
  at okhttp3.Handshake$Companion.a(SourceFile:157)
I/... System.exit called, status: 10
```

OkHttp got `null` for the TLS cipher suite because wolfSSL's Java provider (wolfJSSE, which ATL uses for all Java TLS) was asked about a TLS session whose native object had **already been freed**:

```text
SEVERE: null
java.lang.IllegalStateException: Object has been freed
  at com.wolfssl.WolfSSLSession.getVersion(WolfSSLSession.java:1418)
  at com.wolfssl.provider.jsse.WolfSSLImplementSSLSession.getProtocol(WolfSSLImplementSSLSession.java:493)
  at com.wolfssl.provider.jsse.WolfSSLSocket.startHandshake(WolfSSLSocket.java:1190)
  at okhttp3.internal.connection.a.g(SourceFile:92)
java.lang.IllegalStateException: Object has been freed
  at com.wolfssl.WolfSSLSession.cipherGetName(WolfSSLSession.java:1878)
  at com.wolfssl.provider.jsse.WolfSSLImplementSSLSession.getCipherSuite(WolfSSLImplementSSLSession.java:477)
```

wolfJSSE logs these at `SEVERE` and returns `null` instead of throwing, which is how a native-memory problem turns into OkHttp's `cipherSuite == null`.

---

## Why it happens

1. Disney+ starts several HTTPS requests at once through OkHttp: its start-up backend (`BffStartUpRepositoryImpl`), Firebase, and others.
2. Just before the first failure, the log shows wolfJSSE resolving **`WolfSSLSession_setSession` and `WolfSSLSession_getSession`** for the first time. Those are the JNI calls for **TLS session resumption**, which reuses a cached session from an earlier connection to the same host.
3. wolfJSSE keeps a Java-side session cache (`WolfSSLAuthStore` / `WolfSSLImplementSSLSession`). If a cached `WolfSSLImplementSSLSession` still points at the `WolfSSLSession` (native `WOLFSSL*`) of a connection that has since closed and been freed, the next socket that resumes from it gets back a session wrapper whose `getProtocol()` and `getCipherSuite()` touch freed memory. wolfJSSE guards this with "Object has been freed".
4. OkHttp builds its `Handshake` object from `session.getCipherSuite()`. It gets `null`, throws `IllegalStateException("cipherSuite == null")`, and nothing in the app catches it on that thread. Crashlytics records it and calls `System.exit(10)`.

The CA bundle isn't the problem: `/etc/ssl/certs/ca-certificates.crt` (used through the recipe's host-certificates patch) and `/etc/ssl/certs/java/cacerts` both exist on this machine. A certificate failure would also show up as `SSLHandshakeException`, not "Object has been freed".

**Unconfirmed:** a handshake that failed earlier and closed (freed) the socket's session would produce the same symptom. The diagnostic below tells the two apart.

## Diagnostic

ATL passes `-X <option>` through to ART, the same way ApkManager's debug mode passes `-X -verbose:jni`. wolfJSSE's verbose logging is controlled by Java system properties:

```bash
"~/Applications/Android Translation Layer" \
    ~/Applications/android/com.disneyplus.mea.from.Aptoide.universal.apk \
    -X -Dwolfjsse.debug=true -X -Dwolfssl.debug=true 2>&1 | tee /tmp/disney-tls.log
```

Look for `session resumed` / `resuming session` just before the first "Object has been freed". That points to resumption. An `SSLHandshakeException` or an alert code points to a real handshake failure.

## Suggested fixes in the runtime

All of these are in art_standalone's bundled `external/wolfssljni`, which the ATL.edge recipe builds from art_standalone `master`.

### 1. Don't hand out sessions whose native object is gone (wolfssljni)

In `WolfSSLImplementSSLSession`, treat a freed `WolfSSLSession` as "no session" and fall back to the values recorded at handshake time, instead of returning `null`:

```java
// WolfSSLImplementSSLSession.java
private String cachedCipherSuite;
private String cachedProtocol;

/* call at the end of a successful handshake, while ssl is still valid */
protected void cacheHandshakeInfo() {
    try {
        cachedCipherSuite = this.ssl.cipherGetName();
        cachedProtocol = this.ssl.getVersion();
    } catch (IllegalStateException e) {
        /* already freed; leave the cache empty */
    }
}

@Override
public synchronized String getCipherSuite() {
    try {
        return this.ssl.cipherGetName();
    } catch (IllegalStateException e) {
        return cachedCipherSuite;
    }
}

@Override
public synchronized String getProtocol() {
    try {
        return this.ssl.getVersion();
    } catch (IllegalStateException e) {
        return cachedProtocol;
    }
}
```

Call `cacheHandshakeInfo()` from `WolfSSLSocket.startHandshake()` right after `doHandshake` succeeds, before line 1190's logging.

### 2. Make resumption bind to the new socket's native session (wolfssljni)

When `WolfSSLEngineHelper` resumes from the Java session cache, it should copy only the *resumption data* (the `WOLFSSL_SESSION*` from `wolfSSL_get1_session`) into the new connection. It should never keep a reference to the previous connection's `WolfSSLSession`. If the wolfssljni copy in art_standalone predates upstream wolfssljni's fixes for session-cache lifetime, updating `external/wolfssljni` to the current upstream release is the cleanest fix.

### 3. Workaround: turn off client session resumption

Resumption is an optimization, so turning it off avoids this whole class of bug. In ATL's startup (where it installs wolfJSSE as the default provider), or as a `-X -D…` option:

```java
// e.g. in ATL's provider setup, before the app's first TLS connection
java.security.Security.setProperty("wolfjsse.clientSessionCache.disabled", "true");
```

Check the exact property name against the wolfssljni version in art_standalone (`grep -r clientSessionCache external/wolfssljni`). If that version has no switch, have `WolfSSLEngineHelper` skip the `setSession` call.
