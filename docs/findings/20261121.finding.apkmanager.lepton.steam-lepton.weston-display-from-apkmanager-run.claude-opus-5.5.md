## Short answers

1. **Can ApkManager start Steam with `steam-lepton`?** **Not today.** ApkManager never starts Steam. The Lepton install writes `steam-lepton` and a menu entry, and `run_lepton` only *checks* for `~/.steam/steam.pipe` and asks you to start Steam yourself. Adding it is straightforward, using the existing `spawn_detached` helper (see "What it would take").

2. **Will `steam-lepton` give Lepton a Weston window on this X11 desktop?** It depends on **who launches Lepton**:

   | Lepton launched by | Gets the Weston window? | Why |
   |--------------------|-------------------------|-----|
   | **Steam** (APK added as a non-Steam game, compatibility tool "Lepton (x86_64)", started from Steam's library) | **Yes** | Steam was started with `WAYLAND_DISPLAY=wayland-lepton`, and Lepton inherits Steam's environment |
   | **ApkManager's Run button** | **No, not as the code stands** | Lepton inherits **ApkManager's** environment, which has no `WAYLAND_DISPLAY`, whatever Steam was started with |

## Why ApkManager's Run doesn't get the Weston display

`run_lepton` launches the Lepton wrapper directly:

```vala
yield launch_and_watch(
    { tool.program, "waitforexitandrun", "--", apk_path },
    (launcher) => {
        launcher.setenv("SteamAppId", app_id, true);
        launcher.setenv("STEAM_COMPAT_DATA_PATH", compat, true);
        launcher.setenv("STEAM_COMPAT_CLIENT_INSTALL_PATH", tool.steam_root, true);
        launcher.setenv("STEAM_COMPAT_INSTALL_PATH", Path.get_dirname(apk_path), true);
    },
    ...
```

The `SubprocessLauncher` passes on ApkManager's own environment plus those four Steam variables. Steam is not involved in this process tree, so whatever environment Steam was started with never reaches Lepton.

ApkManager's environment on this machine (read from the running process):

```text
XDG_SESSION_TYPE=x11
DISPLAY=:0
(no WAYLAND_DISPLAY)
```

Lepton then chooses its display (`liblepton.sh`):

```bash
local HOST_WAYLAND_DISPLAY="${WAYLAND_DISPLAY:-}"
export WAYLAND_DISPLAY="${GAMESCOPE_WAYLAND_DISPLAY:-gamescope-0}"
if [[ ! -e "${XDG_RUNTIME_DIR}/${WAYLAND_DISPLAY}" && -n "${HOST_WAYLAND_DISPLAY}" \
      && -e "${XDG_RUNTIME_DIR}/${HOST_WAYLAND_DISPLAY}" ]]; then
    export WAYLAND_DISPLAY="${HOST_WAYLAND_DISPLAY}"
fi
```

With no inherited `WAYLAND_DISPLAY`, it stays on `gamescope-0`. `mounting.sh` line 637 then mounts that socket unconditionally:

```bash
podman_mount_entry "${XDG_RUNTIME_DIR}/${WAYLAND_DISPLAY}" "/waydroid/xdg/wayland-0" rw,U
```

`/run/user/1000/gamescope-0` doesn't exist, so even with Weston running and Steam started through `steam-lepton`, a Run from ApkManager would fail. The error would be Podman's `statfs … no such file or directory`, this time for `gamescope-0` instead of `steam.pipe`. Lepton never looks for Weston's `wayland-lepton` socket by name; it only uses what it inherits.

## What works today, without code changes

After re-running the install:

1. Start **Steam (Lepton)** from the menu, or run `steam-lepton`. A Weston window opens, and Steam starts with `WAYLAND_DISPLAY=wayland-lepton`. Sign in to Steam.
2. In Steam: *Games → Add a Non-Steam Game…*, set the file filter to "All Files", pick the `.apk`. Then in its *Properties → Compatibility*, choose **Lepton (x86_64)**.
3. Press **Play** in Steam. Lepton inherits Steam's `WAYLAND_DISPLAY`, mounts `/run/user/1000/wayland-lepton`, and the app draws inside the Weston window.

ApkManager's **Run** with Lepton will still fail at the display mount on this X11 desktop until ApkManager passes the Weston display itself.

## Update: implemented (November 21, 2026)

After this finding, the user chose to implement it. `run_lepton` in `src/core/runtime_runner.vala` now does the following before launching Lepton:

| Step | Behaviour |
|------|-----------|
| `ensure_wayland_display()` | In a Wayland session, uses the session's `WAYLAND_DISPLAY`. On X11, uses `$XDG_RUNTIME_DIR/wayland-lepton` (the `steam-lepton` socket). If it isn't there, starts `weston --backend=x11 --socket=wayland-lepton --width=1280 --height=800` and waits up to 5 s for the socket. If Weston isn't installed: "Lepton draws on Wayland, and this desktop is X11. Install Weston (re-run the Lepton install, or: sudo apt install weston), then try again." |
| `ensure_steam()` | Steam counts as running when `~/.steam/steam.pipe` exists **and** the PID in `~/.steam/steam.pid` is alive. If not, starts `steam` with `WAYLAND_DISPLAY` set to the same display (so Steam-library launches also use Weston) and waits up to 120 s. Otherwise: "Steam is still starting. Finish any update and sign in to Steam, then press Run again." A Steam that is already running is left alone (no restart) |
| Launch | Lepton gets `WAYLAND_DISPLAY` from ApkManager directly, so Steam's own environment no longer matters for Run |

This replaced the earlier "Lepton needs the Steam client…" check. `spawn_detached` gained an optional environment setup.

### Tested

These tests used a small program calling `RuntimeRunner.run(LEPTON, …)`, built from the same core sources:

| Scenario | Result |
|----------|--------|
| X11, Weston not installed (this machine today) | Weston message above, immediately |
| X11, stand-in `weston` and `steam` (Steam ready after 3 s) | Weston started with the expected arguments; Steam started with `WAYLAND_DISPLAY=wayland-lepton`; Run waited for Steam, then launched Lepton |
| Lepton run directly with that display and Steam pipe | Got past the `steam.pipe` and Wayland mounts and began booting the container |

### Further Lepton incompatibilities found while testing

Booting exposed more places where the x86_64 port expects newer container tools than Ubuntu 24.04 / Mint 22 ship. These were handled the same way as `setpgid` and `ptmxmode`: a conditional patch in `LEPTON_COMPAT_STEPS` and `lepton.conf`, applied to this machine's install, with the release tarball's original behaviour kept on newer systems.

| Error | Cause | Fix |
|-------|-------|-----|
| `runc create failed: … failed to update /proc/…/uid_map: Invalid argument` | Podman 4.9 can't start containers with `--userns=keep-id:uid=0,gid=0` (also fails for a plain BusyBox container) | On Podman 4, omit it (`LEPTON_USERNS_ARG=""`). Podman's default rootless mapping (`0 → 1000`, then the 65,536 subordinate IDs) is identical |
| `pasta: unrecognized option '--no-splice'` | passt `0.0~git20240220` predates `--no-splice` | Leave it out when `pasta --help` doesn't list it (`LEPTON_PASTA_NO_SPLICE=""`) |
| **`pasta failed with exit code 1: Port forwarding mode 'none' conflicts with previous mode`** | Podman 4.9 adds its own pasta port options that clash with Lepton's `-t auto -u auto` and port publishing | **Not fixed.** Patching stopped here: each fix uncovered another gap between Lepton's target (SteamOS: Podman 5, current passt) and Mint 22 |

So on this machine, ApkManager's side now works (display, Weston, Steam), but **Lepton still can't boot its container** with Ubuntu 24.04's Podman 4.9 and passt. Realistic ways forward are newer Podman/passt packages (for example from a backports PPA, or a newer Ubuntu/Mint base) or a distribution Lepton targets (Fedora, Arch). Waydroid uses LXC rather than Podman and pasta, so these particular gaps don't apply to it, and it can use the same nested Weston (not tested here).

## What it would take for ApkManager's Run to do this (original analysis, now implemented)

Three small changes in `runtime_runner.vala`, all in `run_lepton`:

| Change | Detail |
|--------|--------|
| Pass a Wayland display to Lepton | If ApkManager has no `WAYLAND_DISPLAY` but `$XDG_RUNTIME_DIR/wayland-lepton` exists, add `launcher.setenv("WAYLAND_DISPLAY", "wayland-lepton", true)`. In a Wayland session ApkManager's own `WAYLAND_DISPLAY` is already inherited, so nothing changes there |
| Start Weston and Steam when missing | If the Weston socket or the Steam pipe is missing and `~/.local/bin/steam-lepton` exists, start it with the existing `spawn_detached` helper. `steam-lepton` already starts Weston only if its socket is missing, and starts Steam pointed at it |
| Wait, then launch | Poll for both `wayland-lepton` and `~/.steam/steam.pipe` (Steam's first start updates itself and can take minutes, and needs a sign-in), then run Lepton as now; otherwise show a clear message |

### Caveats

- **`steam-lepton` restarts a running Steam** (`steam -shutdown`) so that Steam picks up `WAYLAND_DISPLAY`. ApkManager shouldn't call it when Steam is already running and the Weston socket exists. When ApkManager passes `WAYLAND_DISPLAY` itself, Steam's own environment no longer matters for ApkManager's Run, so ApkManager could start just Weston (`weston --backend=x11 --socket=wayland-lepton …`) and leave a running Steam alone.
- **`~/.steam/steam.pipe` existing doesn't prove Steam is running.** It's a FIFO that Steam creates and may leave behind after it exits. Checking for a `steam` process (or Steam's PID file `~/.steam/steam.pid`) would be more reliable.
- **First Steam start** downloads its runtime and asks for a sign-in, so an automatic start from ApkManager can't finish unattended the first time.
- **The Weston window** has to stay open while the app runs. Closing it closes the app.
