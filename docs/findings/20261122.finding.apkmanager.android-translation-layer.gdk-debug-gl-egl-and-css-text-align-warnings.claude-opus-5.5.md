## 1. `Unrecognized value "gl-egl". Try GDK_DEBUG=help`

### What it is

```text
Unrecognized value "gl-egl". Try GDK_DEBUG=help
```

This is GTK's environment-variable parser. `GDK_DEBUG` holds a comma-separated list of debug flags, and GTK prints this line for any flag it doesn't recognize, then ignores it. In every capture the export's `environment` block shows ApkManager passed it:

```json
"environment" : { "ANDROID_LOG_TAGS" : "*:v", "GDK_DEBUG" : "gl-egl" }
```

### Why it comes up

ApkManager adds the flag on X11 sessions:

```vala
// src/core/runtime_runner.vala
// On X11, GTK inside ATL picks GLX unless this is set, and the app's GL surface stays blank.
if (Environment.get_variable("XDG_SESSION_TYPE") == "x11") {
    launcher.setenv("GDK_DEBUG", "gl-egl", false);
}
```

That was correct for GTK up to 4.14, which used GLX on X11 unless `gl-egl` asked for EGL. ATL needs EGL because Android apps render through EGL. **GTK 4.16 made EGL the default on X11 and removed `gl-egl` and `gl-glx`.** GLX can still be chosen with `GDK_DISABLE=egl`.

The ATL AppImage doesn't use the host's GTK. It bundles its own:

```text
$ "~/Applications/Android Translation Layer" --appimage-mount
/tmp/.mount_Andro…/lib/libgtk-4.so.1.2400.1          ← GTK 4.24.1
```

Its list of accepted `GDK_DEBUG` flags (read from the library) has `gl-api`, `gles-api`, `gl-prefer-gl`, `gl-debug`, `vulkan` and others, but no `gl-egl` or `gl-glx`. The host's `/usr/lib/x86_64-linux-gnu/libgtk-4.so.1` (4.14.5) still has both.

Running the AppImage on this X11 session **without** the flag, with `GDK_DEBUG=opengl`, shows GTK choosing EGL by itself:

```text
EGL API version 1.5 found
 - Client APIs: OpenGL OpenGL_ES
	EGL_ANDROID_blob_cache
	EGL_EXT_buffer_age
	…
```

So the flag has no effect on any AppImage build of ATL: ATL.edge, or pkgforge-dev's, which is built on Arch with a current GTK.

### How to fix it (ApkManager)

The flag still matters in one case: a distro-packaged ATL (`/usr/bin/android-translation-layer`) linked against the host's GTK, when that GTK is older than 4.16. ApkManager links the same host GTK, so `Gtk.get_minor_version()` gives that GTK's version. An AppImage can be recognized by the type 2 marker `AI\x02` at byte 8. The installed ATL here has it:

```text
$ head -c 11 "$(readlink -f ~/.local/bin/android-translation-layer)" | od -c
0000000 177   E   L   F 002 001 001  \0   A   I 002
```

`src/core/runtime_runner.vala`:

```vala
        // GTK before 4.16 picks GLX on X11 unless asked for EGL; 4.16 made EGL the default and
        // dropped the gl-egl flag. AppImages bundle their own (newer) GTK.
        private static bool atl_needs_gl_egl(string program) {
            if (Environment.get_variable("XDG_SESSION_TYPE") != "x11") {
                return false;
            }
            if (is_appimage(program)) {
                return false;
            }
            return Gtk.get_major_version() == 4 && Gtk.get_minor_version() < 16;
        }

        // Type 2 AppImages carry "AI" and 2 at bytes 8-10 of the ELF header.
        private static bool is_appimage(string program) {
            try {
                var stream = File.new_for_path(program).read();
                var header = new uint8[11];
                size_t got;
                stream.read_all(header, out got);
                return got == 11 && header[8] == 'A' && header[9] == 'I' && header[10] == 2;
            } catch (Error e) {
                return false;
            }
        }
```

Then at both call sites:

```vala
            yield launch_and_watch({ program, apk_path }, (launcher) => {
                if (atl_needs_gl_egl(program)) {
                    launcher.setenv("GDK_DEBUG", "gl-egl", false);
                }
            }, (owned) late_failure);
```

```vala
            string[] environment = { "ANDROID_LOG_TAGS=*:v" };
            if (atl_needs_gl_egl(program)) {
                environment += "GDK_DEBUG=gl-egl";
            }
```

Also update the install guide in `runtime_install_dialog.vala` line 591, which tells users to "launch with GDK_DEBUG=gl-egl" on X11. Something like: "A GTK 4 desktop (GTK before 4.16 on X11 needs GDK_DEBUG=gl-egl; the AppImages don't)".

The simpler alternative is to remove the flag entirely. ApkManager only installs AppImage builds, so this would only affect someone using an old distro package on X11.

## 2. `Theme parser error: default-stylesheet.css:21:2-12: No property named "text-align"`

### What it is

```text
(android-translation-layer:…): Gtk-WARNING **: …: Theme parser error: default-stylesheet.css:21:2-12: No property named "text-align"
(android-translation-layer:…): Gtk-WARNING **: …: Theme parser error: default-stylesheet.css:25:2-12: No property named "text-align"
(android-translation-layer:…): Gtk-WARNING **: …: Theme parser error: default-stylesheet.css:29:2-12: No property named "text-align"
```

GTK's CSS parser warns once for each declaration it can't use. `21:2-12` means line 21, columns 2–12, which is the word `text-align`. ApkManager flags these as errors because of the `Gtk-WARNING` prefix, which is why every export lists three "errors" before anything else.

### Why it comes up

At start-up ATL loads its own stylesheet for the whole app:

```c
// ATL src/main-executable/main.c:499
gtk_css_provider_load_from_resource(cssProvider, "/com/gitlab/android-translation-layer/android-translation-layer/default-stylesheet.css");
```

```css
/* ATL src/main-executable/css/default-stylesheet.css */
.ATL-text-align-left > * {
	text-align: left;      /* line 21 */
}

.ATL-text-align-center > * {
	text-align: center;    /* line 25 */
}

.ATL-text-align-right > * {
	text-align: right;     /* line 29 */
}
```

**GTK's CSS has never had `text-align`.** It supports a subset of web CSS for styling (colors, fonts, borders, margins), but text alignment belongs to the widgets: `GtkLabel:xalign` and `GtkLabel:justify` for labels, `GtkEditable:xalign` for text entries. Neighbouring rules in the same file, such as `text-transform`, `font-weight` and `font-style`, *are* GTK CSS properties, which is probably why `text-align` looked safe. The rules date from ATL commit `be93b4c3` (2024-11-26, "JavaWidget: add css classes and default_stylesheet.css").

### What it breaks

The warnings are harmless, but the feature behind them silently does nothing. `View.setTextAlignment()` only switches CSS classes:

```java
// ATL View.java
public void setTextAlignment(int textAlignment) {
	String[] classesToRemove = {"ATL-text-align-left", "ATL-text-align-center", "ATL-text-align-right"};
	native_removeClasses(widget, classesToRemove);
	switch (textAlignment) {
		case TEXT_ALIGNMENT_CENTER:
			native_addClass(widget, "ATL-text-align-center");
			break;
		…
	}
}
```

The classes match no working rule, and every `TextView` label is created left-aligned (`gtk_label_set_xalign(GTK_LABEL(label), 0.f)` in `android_widget_TextView.c`). So any app that centres or right-aligns text with `android:textAlignment` or `setTextAlignment()` shows it on the left: calculator displays, centred headings, button captions drawn as `TextView`s.

### How to fix it (ATL)

Set the alignment on the GTK widgets instead of through CSS.

**1. Remove the three dead rules** from `src/main-executable/css/default-stylesheet.css` (lines 20–30). That removes the warnings.

**2. Make `setTextAlignment()` set the alignment natively.** The CSS selector was `.class > *`, meaning "the widget's direct children". The native version does the same: it walks the children and aligns every label and text entry.

`src/api-impl/android/view/View.java`:

```java
	protected native void native_setTextAlignment(long widget, float xalign);

	public void setTextAlignment(int textAlignment) {
		switch (textAlignment) {
			case TEXT_ALIGNMENT_CENTER:
				native_setTextAlignment(widget, 0.5f);
				break;
			case TEXT_ALIGNMENT_TEXT_START:
			case TEXT_ALIGNMENT_VIEW_START:
				native_setTextAlignment(widget, 0.0f);
				break;
			case TEXT_ALIGNMENT_TEXT_END:
			case TEXT_ALIGNMENT_VIEW_END:
				native_setTextAlignment(widget, 1.0f);
				break;
		}
	}
```

`src/api-impl-jni/views/android_view_View.c`:

```c
JNIEXPORT void JNICALL Java_android_view_View_native_1setTextAlignment(JNIEnv *env, jobject this, jlong widget_ptr, jfloat xalign)
{
	GtkWidget *widget = GTK_WIDGET(_PTR(widget_ptr));
	GtkJustification justify = xalign < 0.25f ? GTK_JUSTIFY_LEFT : xalign > 0.75f ? GTK_JUSTIFY_RIGHT : GTK_JUSTIFY_CENTER;

	for (GtkWidget *child = gtk_widget_get_first_child(widget); child; child = gtk_widget_get_next_sibling(child)) {
		if (GTK_IS_LABEL(child)) {
			gtk_label_set_xalign(GTK_LABEL(child), xalign);
			gtk_label_set_justify(GTK_LABEL(child), justify);
		} else if (GTK_IS_EDITABLE(child)) {
			gtk_editable_set_alignment(GTK_EDITABLE(child), xalign);
		}
	}
}
```

`xalign` positions the text block inside the label, and `justify` aligns the lines of wrapped text within it. Android's alignment does both, so both are set. GtkLabel already mirrors `xalign` for right-to-left languages, which matches Android's "start" and "end". The JNI header is regenerated by the build (`generated_headers/android_view_View.h`), so nothing needs to be added by hand.

The default case (`TEXT_ALIGNMENT_GRAVITY`) is left unchanged. That's where alignment comes from `android:gravity`, and ATL's `TextView` keeps that in its own `gravity` field.

## What to expect after the fixes

- Debug captures start with the app's own output. The four lines now at the top of every export disappear, and ApkManager stops counting three false "errors" per run.
- Text that apps centre or right-align with `textAlignment` appears where they intended.
- Nothing changes in rendering on X11: the AppImage's GTK already uses EGL.
