## Short answer

When Flutter's engine loads, it registers its native methods and caches a list of Android Java classes it will use. One of them is `android.media.Image`, used for platform views and external textures. ATL doesn't provide that class, so `FindClass` fails. Flutter logs `Could not locate Image class`, registration fails, and a `FML_CHECK` on a Flutter worker thread aborts the process.

---

## What the error is

```text
E/flutter (92828): [ERROR:flutter/shell/platform/android/platform_view_android_jni_impl.cc(1211)] Could not locate Image class
Fatal signal 6 (SIGABRT), code -6 (SI_TKILL)
Thread: 92886 "flutter-worker-"
Fault message:
```

The Flutter source at that point:

```cpp
g_image_class = new fml::jni::ScopedJavaGlobalRef<jclass>(
    env, env->FindClass("android/media/Image"));
if (g_image_class->is_null()) {
  FML_LOG(ERROR) << "Could not locate Image class";
  return false;
}
...
g_image_close_method = env->GetMethodID(g_image_class->obj(), "close", "()V");
if (g_image_close_method == nullptr) {
  FML_LOG(ERROR) << "Could not locate close on Image class";
  return false;
}
```

`getHardwareBuffer()` and the `android.hardware.HardwareBuffer` class are optional: Flutter clears the error and continues without them. `Image` and its `close()` method are required.

## Why it happens

I checked every class Flutter's JNI layer looks up against ATL's `api-impl`:

| Class | In ATL? | Flutter's handling |
|------|------|------|
| `android/graphics/Bitmap`, `Bitmap$Config` | yes | required |
| `android/graphics/Path`, `Path$FillType` | yes | required |
| **`android/media/Image`** | **no** | **required (this crash)** |
| `android/hardware/HardwareBuffer` | no | optional |

(`io/flutter/...` classes come from the app itself, and `java/lang/...` classes from ART's core libraries.)

RustDesk's engine is newer than the dahliaOS calculator's. It doesn't have the `dlopen("libandroid.so")` check that fails there, which is why it gets this far.

## Suggested fix in the runtime (ATL)

Add `android.media.Image`. Flutter only calls `close()`, and `getHardwareBuffer()` if it exists, on images it receives from an `ImageReader`. ATL doesn't create real ones, so an abstract class with the public API is enough:

```java
// src/api-impl/android/media/Image.java
package android.media;

import android.graphics.Rect;
import java.nio.ByteBuffer;

public abstract class Image implements AutoCloseable {
	protected Image() {}

	public abstract int getFormat();
	public abstract int getWidth();
	public abstract int getHeight();
	public abstract long getTimestamp();
	public abstract Plane[] getPlanes();
	public abstract void close();

	public void setTimestamp(long timestamp) {}
	public Rect getCropRect() { return new Rect(0, 0, getWidth(), getHeight()); }
	public void setCropRect(Rect cropRect) {}

	public static abstract class Plane {
		protected Plane() {}
		public abstract int getRowStride();
		public abstract int getPixelStride();
		public abstract ByteBuffer getBuffer();
	}
}
```

Optionally add `android.hardware.HardwareBuffer` with a `close()` method, which saves Flutter one cleared exception per start:

```java
// src/api-impl/android/hardware/HardwareBuffer.java
package android.hardware;

public final class HardwareBuffer implements AutoCloseable {
	private HardwareBuffer() {}
	public void close() {}
	public boolean isClosed() { return true; }
}
```

If ATL ever implements `ImageReader` (camera, video frames), `Image` gets a concrete subclass then.

### Probably needed next

Flutter's `AccessibilityBridge` refers to `android.view.accessibility.AccessibilityRecord` and `AccessibilityEvent`, which ATL doesn't have either. The dahliaOS calculator hit exactly that after its own first blocker was fixed. Stubs are in `20261122.finding.apkmanager.android-translation-layer.calculator-dahliaos.flutter-libandroid-dlopen-fails.claude-opus-5.5.md`.

## What to expect after the fixes

With `Image` and the accessibility classes in place, Flutter should create its engine and render through ATL's EGL/GTK path. That's what ATL's Flutter support targets, but each app needs testing. RustDesk would also need network access, which works through the host, and screen-capture permission for its "share this screen" side, which ATL doesn't provide. The "connect to another computer" side is the realistic part.
