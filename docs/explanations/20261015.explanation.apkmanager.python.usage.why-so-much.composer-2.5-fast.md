## 1. Executive summary

**ApkManager is not a Python application.** The shipped GUI, store search, decode pipeline, install logic, and preferences are written in **Vala** and compiled to a native binary (`apk-manager`). End users need **GTK, Java (for Apktool), and libarchive** — not Python.

If the repository looks “full of Python,” that impression almost always comes from **`.venv-gplay/`**: a local virtual environment (~40 MB, **~1,600 tracked files** in git at the time of this writing) created during a **removed Aurora OSS / Google Play prototype**. That folder contains PyPI packages (`gpapi`, `protobuf`, `cryptography`, `requests`, and their dependencies). It is **not** invoked by the current Vala codebase.

In short:

| Layer | Language | Role in ApkManager today |
|-------|----------|---------------------------|
| GUI + business logic | **Vala** | Everything users interact with |
| APK decode | **Java** (`apktool.jar` subprocess) | Full / quick decode |
| Get APKs (F-Droid, Aptoide, …) | **Vala** (`HttpClient`, regex, `json-glib`) | Search and download |
| Build system | **Python** (Meson) | Developer machine only; runs `meson compile`, not bundled in the app |
| `.venv-gplay/` | **Python** (third-party libs) | **Prototype artifact**; should not be treated as part of the product |

## 2. What the application actually runs

### 2.1 Native Vala shell

All sources under `src/` compile into one executable. Dependencies are GObject/GTK stack libraries:

- `libadwaita-1`, `gtk4`, `gio-2.0`, `json-glib-1.0`, `libarchive`, `cairo`, `gtksourceview-5`

There are **zero** references to `python`, `python3`, `.venv-gplay`, or `gpapi` in `src/` today.

### 2.2 Java for Apktool only

Decode uses the same subprocess pattern as many CLI tools:

```text
java -jar <prefix>/lib/apk-manager/apktool.jar d …
```

That is **Java**, not Python. The JAR is fetched at build time by `scripts/fetch-apktool.sh` (bash).

### 2.3 Get APKs without Python

Current store integrations (F-Droid, Aptoide, IzzyOnDroid, OpenAPK, APKMirror, Uptodown browser hand-off) are implemented entirely in `src/core/apk_store_search.vala`:

- HTTP GET/POST via `HttpClient`
- HTML scraping with `GLib.Regex`
- JSON parsing with `json-glib`

Those sources expose **HTML or JSON**, which Vala already handles. No protobuf, no Google FDFE, no Python helper required.

## 3. Where the Python actually is (and why it looks like “so much”)

### 3.1 `.venv-gplay/` — the main culprit

During exploration of **Aurora OSS / Google Play** as a Get APKs source, a virtual environment was created and populated with:

| Package | Why it was installed |
|---------|----------------------|
| `gpapi` | Unofficial Python client for Google Play’s **FDFE** API (protobuf over HTTPS) |
| `protobuf` | Required by `gpapi` generated `_pb2.py` modules |
| `cryptography`, `cffi`, `pycparser` | Transitive deps of TLS / crypto stacks |
| `requests`, `urllib3`, `certifi`, `charset_normalizer`, `idna` | HTTP client stack for `gpapi` |

The prototype design (documented in [the Aurora explanation](./20261013.explanation.apkmanager.auroraoss.google-play.frontend.python.grok-4.7.md)) was:

```text
Vala (Get APKs UI)
    → spawn python3 scripts/aurora_play_download.py …
        → gpapi speaks FDFE protobuf to android.clients.google.com
    → stdout JSON with version codes / download path
    → Vala installs APK like any other store
```

That script and the Vala wiring were **removed** when Aurora was rolled back. The **venv was left in the tree** and, importantly, **committed to git** — so every clone carries hundreds of `.py` files under `.venv-gplay/lib/python3.12/site-packages/` even though the app never calls them.

**This is a repository hygiene issue, not an architectural choice.** Standard practice:

- Add `.venv-gplay/` (or `.venv*/`) to `.gitignore`
- Remove the venv from version control
- Recreate locally only if Google Play integration is revived

### 3.2 Meson (build-time Python)

`meson compile` and `meson install` are driven by Meson, which is **written in Python** and installed as `/usr/bin/meson` on Debian/Fedora. Error logs in `docs/errorsSolutions/` sometimes show paths like `/usr/lib/python3.14/site-packages/mesonbuild/…` — that is the **build tool**, not ApkManager runtime code.

Developers need Python on the machine to run Meson; **users who install a packaged `apk-manager` binary do not.**

### 3.3 Early methodology mention (never shipped)

One early methodology draft suggested parsing `apktool.yml` via a temporary `python3 -c` one-liner because `json-glib` does not read YAML. The unified plan and current code use other approaches (manifest parsing from decode output / binary XML). **No YAML-via-Python helper exists in the repo.**

## 4. Why Python was considered at all (Google Play / Aurora)

The Aurora explanation doc covers this in depth; the condensed version:

| API surface | Format | Vala-friendly? |
|-------------|--------|----------------|
| F-Droid / Aptoide / Izzy HTML or JSON | Text | Yes — already implemented |
| Google Play **web search** | HTML | Yes — could scrape in Vala |
| Google Play **FDFE download API** | **Protocol Buffers** (binary) | **No** — no protobuf stack in Vala deps |

Google’s download path is not a plain `.apk` URL. It requires authenticated FDFE calls (`details`, `delivery`, `purchase`, …). Reimplementing that in Vala would mean:

1. Maintaining `.proto` definitions and a code generator, or
2. Hand-rolling binary protobuf framing, or
3. Binding an existing C library (none is a standard distro dependency)

**Python won the prototype** because `gpapi` already implements FDFE and Aurora-style anonymous auth. The intended integration pattern matched ApkManager’s existing philosophy: **keep the GUI native; delegate specialist protocols to a small subprocess** (same as `java -jar apktool.jar`).

Aurora was removed; the **reason Python was attractive for that one feature** remains valid if Play integration returns.

## 5. Subprocess pattern: when a second language is acceptable

ApkManager’s architecture deliberately avoids embedding every protocol in Vala:

```text
┌─────────────────────────────────────┐
│  apk-manager (Vala / GTK)           │
│  sessions · UI · HTTP stores · cache│
└──────────┬──────────────┬───────────┘
           │              │
     java -jar          (optional future)
     apktool.jar        python3 helper
           │              │
           ▼              ▼
     decode APK      FDFE / specialist API
```

Python is **not** the primary implementation language. It appears only when:

1. A mature library exists in another ecosystem (Apktool → Java; FDFE → `gpapi` → Python), and
2. Rebuilding that library in Vala is poor return on effort, and
3. The call is isolated behind a subprocess with a stable JSON/text contract.

That is **optional glue**, not “ApkManager is written in Python.”

## 6. File-count reality check

Approximate breakdown of Python-visible files in a typical checkout:

| Location | Approx. count | Part of product? |
|----------|---------------|------------------|
| `.venv-gplay/lib/python3.12/site-packages/**/*.py` | ~700+ source files (+ `.pyc`, dist-info) | **No** — vendored PyPI deps |
| `src/**/*.vala` | ~30 files | **Yes** — the app |
| `scripts/*.sh` | 2 files | **Yes** — build/install helpers (bash, not Python) |
| Project-owned `scripts/*.py` | **0** (after Aurora removal) | N/A |

So “so much Python” is almost entirely **third-party site-packages accidentally versioned**, not application logic.

## 7. What users and packagers should assume

### End-user runtime

```bash
apk-manager --version   # native binary
apk-manager foo.apk     # Vala + libarchive + optional Java
```

No `python3` dependency for normal use.

### Developer checkout

- **Required:** Vala toolchain, Meson (Python-based installer), Ninja, GTK/Java dev packages per `README.md`
- **Not required for current features:** `.venv-gplay`, `pip`, `gpapi`
- **Safe to delete:** `.venv-gplay/` unless actively working on Google Play integration

### Distro packaging

A `.deb` / `.rpm` should ship:

- `apk-manager` binary
- `apktool.jar` under `/usr/lib/…/apk-manager/`
- Desktop file, icons, GSettings schema

It should **not** ship `.venv-gplay` or declare a Python dependency for ApkManager itself.

---

## 8. Recommendations

1. **Stop tracking `.venv-gplay/` in git** — add to `.gitignore` and remove from the index (`git rm -r --cached .venv-gplay`). This immediately reduces perceived “Python surface area” by ~1,600 files.
2. **Keep the Vala-first rule** from the unified methodology: new store sources that speak HTML/JSON stay in `apk_store_search.vala`.
3. **If Aurora / Play returns**, reintroduce a **single** `scripts/aurora_play_download.py` (or similar) plus documented venv setup in `docs/requirements/` — not a committed `site-packages` tree.
4. **Do not add Python** for tasks Vala already covers (HTTP, JSON, regex, file I/O, GSettings).

---

## 9. Bottom line

| Question | Answer |
|----------|--------|
| Is ApkManager written in Python? | **No** — it is Vala/GTK with Java (Apktool) for decode. |
| Why does the repo contain thousands of `.py` files? | Mostly **`.venv-gplay/`**, a committed virtualenv from an **removed** Google Play prototype. |
| Does the running app use Python? | **Not today** — no Python subprocess in `src/`. |
| When would Python make sense here? | Only for **specialist protocols** (e.g. FDFE/protobuf via `gpapi`) where Vala has no practical library — as a **small helper**, not the main codebase. |
| What should I do if the Python volume worries me? | Treat `.venv-gplay` as **local tooling to gitignore**, not as part of ApkManager’s architecture. |

The unified vision remains: **native Linux GUI**, **Apktool as a pinned JAR**, **HTTP stores in Vala**. Python’s footprint in this tree is a **historical prototype artifact and build-tool dependency**, not evidence that the product direction is Python-first.
