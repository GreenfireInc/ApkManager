## 1. Executive summary

Installing a Java runtime on Debian or Fedora lets you run **Java programs** (`.jar` files of JVM bytecode). An Android **APK is not one of those programs**.

An APK is a signed ZIP of Android-specific artifacts. Its code is **Dalvik bytecode** (`classes.dex`), executed by **Android Runtime (ART)**, against the **Android framework** (`android.*` APIs), inside an Android process model (Zygote, Binder, permissions, a system image). OpenJDK’s `java` command does not implement any of that. It can launch **Apktool**, which is a normal JAR, and Apktool only **decodes** the APK into files you can read. Decode output is not a runnable Linux application.

---

## 2. What `java` actually runs

A Java runtime (OpenJDK on Fedora or Debian) provides:

- A Java Virtual Machine that loads **JVM bytecode** (`.class` files, usually packed in a `.jar`).
- The **Java SE** class library (`java.*`, `javax.*`, and a few `jdk.*` packages).
- A launcher: `java -jar some-tool.jar`.

Apktool 2.9.3 is that kind of tool. ApkManager starts it roughly as:

```text
java -jar apktool.jar d -f -o <decoded-dir> <file.apk>
```

That process is a desktop Java program. It reads the APK as data, writes smali, decoded XML, and `apktool.yml`, then exits. The APK’s own code never becomes the process that `java` is running.

---

## 3. What is inside an APK

| Piece | What it is | Why `java` cannot execute it |
|-------|------------|------------------------------|
| `classes.dex` (and `classesN.dex`) | Dalvik Executable bytecode | Different instruction set and file format from JVM `.class` files. The HotSpot VM does not load DEX. |
| `AndroidManifest.xml` | Binary Android XML | Not a Java entry point. Names the package, components, permissions, and SDK levels for Android’s package manager. |
| `resources.arsc` and `res/` | Compiled Android resources | Resolved by Android’s resource system, not by the JRE. |
| `lib/<abi>/*.so` | Native code built for Android ABIs | Linked against Android’s **Bionic** C library and Android system libraries, not against glibc on a normal Linux desktop. |
| `META-INF/` | JAR-like signing (v1) plus APK Signature Scheme v2/v3 blocks | Proves the package to Android’s installer. It does not make the archive a `java -jar` program. |
| `assets/` | Opaque app files | Loaded through Android `AssetManager`. |

A `.jar` and an `.apk` are both ZIP archives, and both can carry a `META-INF` signature. That shared packaging is why the formats look related. The bytecode and the platform libraries inside them are not interchangeable.

---

## 4. DEX is not JVM bytecode

Android apps are usually written in Java or Kotlin, then compiled to JVM `.class` files **and then translated** by `d8` / `r8` into `classes.dex`. That second step is lossy from the JVM’s point of view: registers instead of an operand stack, a different constant pool, a different type system on the wire, and a different file that can hold many classes in one image.

ART (and, historically, the Dalvik VM) is the machine that interprets or ahead-of-time compiles DEX. It ships inside Android. It is not the `java` binary from `java-latest-openjdk` or `default-jre`.

Tools can translate DEX back toward JVM bytecode (`dex2jar` and similar) or to smali text (what Apktool/baksmali does). A translated JAR still fails on a desktop JRE for the reason in the next section: the calls inside it are Android framework calls.

---

## 5. The Android framework is not the Java standard library

Application code calls types such as `android.app.Activity`, `android.content.Context`, `android.os.Bundle`, and `android.view.View`. Those packages are not part of Java SE. They are implemented by the Android system image (framework, system server, and native services).

The `android.jar` developers compile against is a set of **stubs** for the compiler. The real methods run only after the package is installed on a device or emulator that contains that framework. A desktop JRE has no `Activity` lifecycle, no `PackageManager`, and no implementation of those APIs, so even a perfectly converted JAR has nowhere to bind those calls.

---

## 6. The process model is Android’s, not a `main` method

A typical Java program starts at `public static void main`. An Android app does not. The system:

1. Verifies the APK signature and installs it under an Android user id.
2. Starts the app by forking from **Zygote**, which has already loaded the framework.
3. Delivers **Intents** to components declared in the manifest (`Activity`, `Service`, `BroadcastReceiver`, `ContentProvider`).
4. Talks to system services over **Binder**.
5. Applies the permission model, notifications, and background limits from the manifest and the OS version.

None of those steps exist in a Linux Java runtime. There is no Android package manager, no Zygote, and no Binder services behind the `java` command.

---

## 7. Native libraries and the C library

Many APKs ship `.so` files under `lib/arm64-v8a`, `lib/armeabi-v7a`, `lib/x86_64`, or `lib/x86`. Those binaries are built for Android’s ABI and link to **Bionic**, Android’s libc, plus libraries such as `liblog`, `libandroid`, and `libjnigraphics`.

A Fedora or Debian userspace uses **glibc**. Copying `lib/x86_64/libfoo.so` next to a Java process and hoping `System.load` works fails the dynamic linker: unresolved Android symbols, a different libc, and often a different set of allowed syscalls and filesystem layout (`/system`, `/data`, app-private storage). CPU architecture can be a second mismatch (an `arm64-v8a` library on an x86_64 PC).

---

## 8. What people use when they do want the app to run

Running the app means providing an Android environment, not a larger Java heap:

| Approach | What it actually supplies |
|----------|---------------------------|
| Android Emulator, physical device, `adb install` | A full Android system image: ART, framework, package manager |
| Waydroid (and older Anbox-style containers) | An Android userspace on Linux, still with ART and Bionic, not OpenJDK |
| Chrome OS ARC / similar compatibility layers | A packaged Android runtime maintained by the vendor |

Those systems boot or contain Android. They do not treat the APK as a JAR.

---

## 9. What ApkManager uses Java for

Java on this project is a **tool runtime**:

- Apktool’s JAR decodes binary manifest XML, disassembles DEX to smali, and can rebuild a modified tree into a new APK.
- ApkManager is a GTK 4 / Libadwaita front end. It does not embed ART and does not install or launch the package.

Quick Manifest and Full Decode succeed when `java` can run Apktool. They are not a test of whether the APK would run. After a successful decode you have files on disk (smali, XML, resources). Opening those files, or double-clicking the original `.apk` in a Linux file manager, still does not start the Android app.

## 10. Short answers to the usual follow-ups

**“The app was written in Java. Why isn’t the JRE enough?”**  
The source language is Java or Kotlin. The shipped artifact is DEX plus Android APIs. The language and the runtime platform diverged at the build step that produced `classes.dex`.

**“Can I `java -jar app.apk`?”**  
No. The archive has no JVM `Main-Class` entry that OpenJDK can execute, and its code is not JVM bytecode.

**“If Apktool can rebuild an APK, did we run it?”**  
No. Rebuild produces another APK for an Android installer. It does not start activities on the Linux desktop.

**“Would a newer Java (17, 21, 25) change this?”**  
No. Apktool needs a modern JDK to run **itself**. No Java SE release loads DEX or ships the Android framework.
