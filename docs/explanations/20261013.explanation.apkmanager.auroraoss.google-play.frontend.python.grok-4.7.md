## 1. Executive summary

Aurora OSS is not an APK repository in the sense F-Droid, IzzyOnDroid, Aptoide, or Uptodown are. [Aurora Store](https://gitlab.com/AuroraOSS/AuroraStore) is an unofficial client for **Google Play**. It searches Google’s catalog, authenticates with a Google account (often an anonymous one supplied by Aurora’s token dispenser), and downloads the APK from Google’s servers.

Adding “Aurora OSS” to Get APKs therefore means adding a **Google Play frontend**, branded with Aurora’s icon and authenticated the way Aurora Store authenticates. It does not mean fetching `index-v1.json` or an F-Droid-style `repo/*.apk` URL from `auroraoss.com`.

The Vala app can scrape the public Play Store search page by itself. Completing a download needs the binary **FDFE** API (`https://android.clients.google.com/fdfe/…`). That API speaks Protocol Buffers, not JSON or HTML. This codebase has no protobuf stack. The practical way to speak FDFE from ApkManager is a small **Python helper** that uses the existing `gpapi` bindings, called as a subprocess — the same pattern ApkManager already uses for `curl` and `java -jar apktool.jar`.

A working prototype of that design was added on October 13, 2026 and then removed when asked to undo Aurora OSS. The pieces below are what that prototype contained, and what a future addition would have to put back.

## 2. Aurora is a door, not a warehouse

Aurora Store’s own README says the distinction directly: Aurora Store does not own, license, or distribute apps. Descriptions, icons, and APK bytes are fetched from Google Play. Aurora Store is the door; Google Play is the warehouse.

| What people might assume | What is actually true |
|--------------------------|------------------------|
| `https://auroraoss.com/` is an app catalog like `https://f-droid.org/` | The site is a project homepage (motto, Aurora Store description, contact). Cloudflare sits in front of it. There is no public app-search index there. |
| Aurora publishes APKs the way IzzyOnDroid does at `https://apt.izzysoft.de/fdroid/repo/` | Aurora does not. IzzyOnDroid and F-Droid *also list* the Aurora Store app (`com.aurora.store`) because someone built that client. That is Aurora-the-app, not Aurora-the-store. |
| “Add the Aurora repository URL” is enough | There is no repository URL to add. The integration has to call Google. |

The other Get APKs sources in this tree are self-contained catalogs:

| Source | Search | Download |
|--------|--------|----------|
| F-Droid | `https://search.f-droid.org/?q=` (HTML) | `https://f-droid.org/api/v1/packages/{id}` then `https://f-droid.org/repo/{id}_{versionCode}.apk` |
| Aptoide | `https://ws2.aptoide.com/api/7/listSearchApps` (JSON) | `https://ws2.aptoide.com/api/7/getApp` → `file.path` |
| IzzyOnDroid | POST `https://apt.izzysoft.de/fdroid/index.php` (HTML) | `https://apt.izzysoft.de/fdroid/api/v1/packages/{id}` then `…/repo/{id}_{versionCode}.apk` |
| Uptodown | `https://en.uptodown.com/android/search` (HTML) | Browser only; their download page requires a browser check |
| Aurora OSS | Google Play’s public search page | Google Play’s private FDFE API, after an Aurora dispenser login |

F-Droid, Aptoide, and IzzyOnDroid answer in HTML or JSON that Vala already parses with `GLib.Regex` and `json-glib`. Aurora’s download path does not.

## 3. The two Google endpoints, and which one is which

There are two different Google surfaces. Mixing them up is how an Aurora integration looks like it “uses Google Play” even though the menu label says Aurora.

### 3.1 Public web search — no login

```text
GET https://play.google.com/store/search?q={query}&c=apps
```

This is the same HTML page a desktop browser shows. It does not require a Google account. A normal browser user-agent is enough; `curl` from this machine returned a full results page for “termux” and “fossify”.

Useful fragments in that HTML:

- Package id: `href="/store/apps/details?id=com.termux"`
- Title: `<div class="vWM94c">Termux</div>` or `aria-label="Termux"` on the card link
- Icon: `https://play-lh.googleusercontent.com/…`
- One-line summary: `<div class="omXQ6c">…</div>`

That page is a storefront. It does not contain an APK URL. “Install” on the web Play Store is an instruction to the user’s signed-in Android device, not a file link.

ApkManager can implement this half entirely in Vala, the same way it scrapes F-Droid and Uptodown: `HttpClient.get_string()` plus a regex over the HTML. Cap the list (about 20 unique package ids). The page repeats the same package id many times (screenshots, ratings, “related” modules), so the parser has to de-duplicate.

### 3.2 FDFE — the Play Store app’s API

```text
https://android.clients.google.com/fdfe/details?doc={package}
https://android.clients.google.com/fdfe/delivery?doc={package}&ot=1&vc={versionCode}
https://android.clients.google.com/fdfe/purchase
https://android.clients.google.com/fdfe/search
```

**FDFE** is the HTTP API inside the official Play Store app (`com.android.vending`, nicknamed Finsky). Aurora Store, and every other unofficial Play client, reverse-engineered this API. Responses are **Protocol Buffer** messages (`ResponseWrapper` → `payload.detailsResponse` / `deliveryResponse`), not JSON.

A successful details call yields:

- `versionName` (for example `1.6.0` for `org.fossify.clock`)
- `versionCode` (an integer, for example `10`, or `142` for Termux)

A successful delivery call yields a short-lived URL:

```text
https://play.googleapis.com/download/by-token/download?token=…
```

That URL is the actual APK bytes. It is minted for the authenticated session and expires. It is not a stable `repo/{package}_{version}.apk` link you can bookmark.

Calling FDFE with no session returns HTTP 400 or 401. Calling it with only a bearer token from a bare `GET /api/auth` also failed in testing (HTTP 400, empty version). The request has to look like a specific Android device: user-agent, GSF id, DFE cookie, and device-check-in tokens. Those come from the dispenser, not from the Vala app.

### 3.3 Why the menu still says Aurora

The user asked for the repository at [auroraoss.com](https://auroraoss.com/). The honest implementation is:

1. Show Aurora’s logo (`public/assets/icons/storesRepositories/appRepo.auroraOSS.svg` is already in the tree; it was not wired into `data/apk-manager.gresource.xml` after the undo).
2. Search the catalog Aurora Store searches, which is Google Play’s catalog.
3. Log in the way Aurora Store logs in anonymously, via Aurora’s dispenser.
4. Download from the URL Google returns.

Label the source **Aurora** so it is distinct from F-Droid and IzzyOnDroid, and say in the README that the bytes come from Google Play. Hiding that would make the feature look like a fifth independent repository when it is not.

## 4. Why Python is needed

Vala in this project talks to the network through `curl` (`src/utils/http_client.vala`) and parses text with `GLib.Regex` or `json-glib`. None of those can decode `googleplay.proto`.

Aurora Store itself does not parse this by hand either. It depends on **gplayapi**, a library of generated protobuf classes, and speaks FDFE from Kotlin. On a desktop, the same generated API exists as the Python package **`gpapi`** (`from gpapi import googleplay_pb2`).

### 4.1 What the helper has to do

1. Load a device profile. Aurora publishes one as a Java `.properties` file, for example [arm64_xxhdpi.properties](https://gitlab.com/AuroraOSS/aurora-dispenser/-/raw/main/resources/arm64_xxhdpi.properties) (Pixel 7a, `arm64-v8a`, SDK 33). POST that JSON object to the dispenser.
2. Read the auth bundle: `authToken`, `gsfId`, `dfeCookie`, `deviceCheckInConsistencyToken`, `deviceConfigToken`, and `deviceInfoProvider.userAgentString`.
3. `GET /fdfe/details?doc={package}` and parse `versionCode` / `versionString` with `ResponseWrapper`.
4. `GET /fdfe/delivery?doc={package}&ot=1&vc={versionCode}` and read `appDeliveryData.downloadUrl`.
5. Download that URL to `{package}_{versionCode}.apk`.

Steps 3 and 4 are the reason Python is in the design. Steps 1, 2, and 5 could be `curl`. Splitting them across two languages means two sessions and two copies of the header logic, so the helper should own the whole download.

### 4.2 Why not parse the protobuf in Vala

A details body is a few kilobytes of binary. `versionName` sometimes appears as ASCII (`1.6.0`), which makes a regex tempting. `versionCode` does not. In a live response it is a protobuf **varint** immediately after the version string:

| Package | versionName | versionCode | Bytes after the name |
|---------|-------------|-------------|----------------------|
| `org.fossify.clock` | `1.6.0` | 10 | `48 ec 8c b4 05` — field tag `0x48`, then a multi-byte varint |
| `com.termux` | `googleplay.2026.10.09` | 142 | `48 b2 ad a3 0c` |

`10` and `142` are not sitting in the file as the text `"10"` or `"142"`. A hand-rolled Vala scanner has to know field numbers inside `AppDetails`, skip nested messages, and decode base-128 varints. Google changes this schema. The next breakage would be a silent wrong version code and a 400 from `/fdfe/delivery`. `gpapi` is the schema, regenerated when Play changes. That is the same bet Aurora Store makes.

### 4.3 The protobuf package pin

`gpapi`’s checked-in `googleplay_pb2.py` was generated by an older `protoc`. Current PyPI `protobuf` 4+ refuses to load it:

```text
TypeError: Descriptors cannot be created directly.
If this call came from a _pb2.py file, your generated code is out of date…
```

The workaround that worked here:

```bash
pip install gpapi 'protobuf<4'
```

or, before import:

```python
os.environ["PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION"] = "python"
```

The pure-Python implementation is slower and still depends on a protobuf 3.x layout. Pin `protobuf<4` in any setup note. `requests` is optional if the helper uses `urllib.request`, which the prototype did, so the hard dependency is `gpapi` plus a compatible `protobuf`.

### 4.4 Why not `apkeep` instead

[apkeep](https://github.com/EFForg/apkeep) can download from Google Play with an Aurora dispenser AUTH token (`--auth-token`, tokens that start with `ya29.`). That would also be a subprocess, with no `gpapi` pin. On this machine `cargo install apkeep` failed because the crate needs Cargo edition 2024 and the installed Cargo was 1.82. Shipping apkeep would mean vendoring a binary or documenting a Rust toolchain. Python 3 is already assumed on Debian and Fedora hosts that build this Vala app. A checked-in script is the smaller dependency.

### 4.5 How ApkManager should call it

Do not import Python into the Vala process. Spawn it:

```text
python3 scripts/aurora_play_download.py info {package}
python3 scripts/aurora_play_download.py download {package} {output_dir}
```

stdout is one JSON object (`version_name`, `version_code`, `download_url`, `apk_path`). stderr carries failures. This matches `HttpClient` spawning `curl` and the decode path spawning `java`.

Resolve the interpreter in this order:

1. `$APK_MANAGER_PYTHON` if set.
2. A project-local virtualenv such as `.venv-gplay/bin/python3` when present (that is where `gpapi` was installed during the prototype; the venv should stay gitignored).
3. `python3` on `PATH`.

If `gpapi` is missing, the helper should exit non-zero with a one-line install instruction. Get APKs should show that string. Search results can still list apps; only download and the “already installed” version check need the helper.

## 5. The Aurora token dispenser

Anonymous mode does not send the user’s Gmail password anywhere. Aurora runs a **token dispenser**: a server that holds volunteer Google accounts, logs one of them into Play on the server side, and hands the client a short-lived auth bundle.

Documented API ([aurora-dispenser](https://gitlab.com/AuroraOSS/aurora-dispenser)):

| Call | Result |
|------|--------|
| `GET https://auroraoss.com/api/auth` with `User-Agent: com.aurora.store-…` | Small JSON: `email` and `auth` (a `ya29.` bearer). **Not enough** for FDFE. Tested details calls returned HTTP 400. |
| `POST https://auroraoss.com/api/auth` with the device-properties JSON and the same user-agent | Full bundle: `authToken`, `gsfId`, `dfeCookie`, `deviceCheckInConsistencyToken`, `deviceConfigToken`, `deviceInfoProvider`, `email`, `isAnonymous`. **This is the call that works.** |

A tiny hand-written profile (`UserReadableName`, `Build.MODEL`, `Platforms`) produced HTTP 500. The full Pixel 7a properties file produced HTTP 200, then FDFE details HTTP 200 for `org.fossify.clock` (version `1.6.0`, code `10`) and a `play.googleapis.com` download URL.

Operational constraints, from Aurora’s own wiki and from this session:

- The dispenser is behind Cloudflare. A generic browser user-agent can be blocked. `com.aurora.store-4.8.4-76` was accepted.
- It rate-limits. Repeated `GET /api/auth` during experimentation returned HTTP 429. Back off; do not call the dispenser once per search result.
- Tokens expire and Google invalidates sessions that are shared across too many clients. Download should fetch a fresh bundle per download, not cache it for days.
- These are real Google accounts operated by Aurora volunteers. Play’s terms allow Google to kill them. Paid apps and apps that use Play Asset Delivery still will not download. Aurora Store documents the same limits.
- The user’s IP is visible to Cloudflare on the dispenser hop. The Play API calls afterward come from the desktop running ApkManager, not from Aurora’s server, unless you deliberately proxy them. Say that in any user-facing note. Aurora’s “insecure anonymous session” is the same idea: the device talks to Google directly.

Check `https://auroraoss.com/api/amiblocked` if every auth call fails. That endpoint is what Aurora’s maintainers tell people to open when they suspect a block.

## 6. What to add in this codebase

The prototype touched the same seams as IzzyOnDroid. A future patch should do the same, and nothing broader.

### 6.1 Source identity

In `src/core/apk_store_result.vala`:

- Add `ApkStoreSource.AURORA` to the enum.
- `source_label` → `"Aurora"`.
- `repository_icon_basename` → `"appRepo.auroraOSS.svg"`.

In `src/core/store_install_registry.vala`, map that enum to the string `"aurora"` in `store_installs.json`, so the existing duplicate-download check can say “already installed from Aurora” without treating it as the same file as the F-Droid build of the same package. F-Droid and Play builds of one app are different signatures and different version codes. They must not collapse into one record.

### 6.2 Search, in Vala

In `src/core/apk_store_search.vala`:

- `search_aurora()` GETs the Play search URL with `HttpClient.BROWSER_USER_AGENT`.
- `parse_aurora_results()` walks `href="/store/apps/details?id=…"`, de-duplicates package ids, and reads title, summary, and `play-lh.googleusercontent.com` icon from the following slice of HTML.
- Append those `ApkStoreResult` rows from `search_all()`.
- Raise the “every source failed” threshold by one (it is `failures == 4` with F-Droid, Aptoide, Uptodown, and IzzyOnDroid).

Do **not** call the dispenser during search. A query can return 20 apps; 20 auth round-trips will trip the rate limit and make the whole Get APKs search feel hung. Version suffixes `(v.X;YYYYMMDD)` can stay empty on Aurora rows unless you later add one details call for the selected row only.

### 6.3 Download, in Python

Add:

- `scripts/aurora_play_download.py` — `info` and `download` subcommands, JSON on stdout.
- `data/aurora/arm64_xxhdpi.properties` — the dispenser device profile, copied from Aurora’s repository so the app does not depend on GitLab at download time.

`download_apk()` for `ApkStoreSource.AURORA` should spawn that script into `AppPaths.downloads_dir` and return the path it prints. `is_already_installed()` needs the same `info` call, because there is no `{package}_{code}.apk` URL to regex until FDFE answers. Cache that info for the selected row so a click does not authenticate twice (selection check, then download check).

Wire the script and the properties file into `data/meson.build` `install_data()` under `share/apk-manager/scripts` and `share/apk-manager/aurora`. Dev builds should find them by walking up from the current directory or `/proc/self/exe`, the way `AppPaths.store_repository_icon()` already finds icons.

### 6.4 UI

In `src/windows/get_apks_window.vala`:

- Dropdown row: `StoreSourceFilterItem("Aurora", "appRepo.auroraOSS.svg")`.
- `active_source_filter()` must use the new index. The dropdown is positional (`get_selected()` is an integer). Inserting Aurora in the middle shifts Uptodown. The current order is All Sources, Aptoide, F-Droid, IzzyOnDroid, Uptodown.
- Subtitle strings that list the sources.

In `data/apk-manager.gresource.xml`, alias `appRepo.auroraOSS.svg` next to the F-Droid, Aptoide, Uptodown, and Izzy icons. The SVG already lives at `public/assets/icons/storesRepositories/appRepo.auroraOSS.svg`.

### 6.5 README

State three facts:

1. Aurora searches and downloads through Google Play.
2. Python 3 with `gpapi` and `protobuf<4` must be installed, or `APK_MANAGER_PYTHON` must point at an environment that has them.
3. Paid apps, Play Asset Delivery, and dispenser rate limits will fail even when search works.

### 6.6 What not to add

- Do not put the user’s Google password in ApkManager. Anonymous dispenser auth is the Aurora path. A personal AAS token is a different product and a higher account-risk.
- Do not vendor `gpapi` or the protobuf runtime inside the Vala binary unless you are ready to own schema updates.
- Do not treat `https://auroraoss.com/` as a fourth F-Droid mirror.
- Do not resolve an APK URL at search time.

## 7. End-to-end flow

```text
User types "fossify" and clicks Search
        │
        ▼
Vala HttpClient GET play.google.com/store/search?q=fossify&c=apps
        │
        ▼
Regex → ApkStoreResult rows (name, package id, icon, summary)
        source = AURORA, page = play.google.com/store/apps/details?id=…
        │
        ▼
User selects org.fossify.clock and confirms download
        │
        ▼
Vala spawns python3 scripts/aurora_play_download.py download org.fossify.clock <downloads dir>
        │
        ├─ POST auroraoss.com/api/auth          (device profile → auth bundle)
        ├─ GET  android.clients.google.com/fdfe/details?doc=org.fossify.clock
        ├─ GET  android.clients.google.com/fdfe/delivery?doc=…&ot=1&vc=10
        └─ GET  play.googleapis.com/download/by-token/download?token=…
        │
        ▼
JSON {"apk_path": "…/org.fossify.clock_10.apk", "version_code": 10, …}
        │
        ▼
Existing ApkInstall.install() copies into ~/Applications/android
StoreInstallRegistry records source=aurora, package, version code
```

Search never leaves Vala. Download never reimplements protobuf in Vala. The Google hostname appears because that is where Aurora Store itself sends the user.

## 8. What a successful probe looked like

These calls were made while the feature was being built, before it was removed:

1. `GET https://play.google.com/store/search?q=termux&c=apps` returned HTML containing `com.termux` and the title Termux. No dispenser, no Python.
2. `GET https://auroraoss.com/api/auth` with the Aurora user-agent returned `{"email","auth"}` only. FDFE details with that bearer alone returned HTTP 400.
3. `POST https://auroraoss.com/api/auth` with the full Pixel 7a properties returned the long auth bundle (`authToken`, `gsfId`, `dfeCookie`, device tokens).
4. Details for `org.fossify.clock` then returned version name `1.6.0` and version code `10`.
5. Delivery returned `https://play.googleapis.com/download/by-token/download?token=…`.

That is the whole integration in one package. Everything else in the GUI is presentation around those five steps.
