## 1. Executive summary

ApkManager **Pass 3** delivered a working GUI: open APKs, browse raw archive contents, run Quick Manifest and Full Decode, manage recent sessions, install from Get APKs, and edit core preferences. The **decode engine and cache already work** — Apktool writes human-readable output to disk.

What is missing is the **second half of the inspection workflow**: after Full Decode, the app still shows the **packed APK** (ZIP) in the Files tab instead of the **decoded project tree**, and there are **no in-app viewers** for the decoded text and binary assets. Framework management (`apktool if` / `lf` / `cf`) and several **GSettings keys** are defined in the schema but not connected to behavior.

The unified methodology treats these as **Phase 3–4** deliverables. Pass 3 closed Phase 1–2 and parts of Phase 3; the items below are the main reason the app still feels like “ZIP browser + decode button” rather than “Apktool GUI like AppManager.”

---

## 2. “Unified methodology vision” — what that phrase means

The [unified methodology](../methodologies/20261007.methodology.unified.apktool.gui.apkmanager.debian.fedora.composer-2.5-fast.md) is the single architecture spec that reconciles earlier ApkManager design documents. Its core model:

| Layer | Responsibility |
|-------|----------------|
| **Native shell (Vala / GTK 4 / Libadwaita)** | Sessions, UI, file picking, progress, viewers |
| **Raw reader (`ApkArchive` / libarchive)** | Instant ZIP listing — no Java |
| **Decode engine (`ApktoolRunner` + pinned `apktool.jar`)** | Subprocess decode into XDG cache |
| **Cache (`~/.cache/apk-manager/…`)** | Decoded trees, frameworks, downloads |
| **Viewers (GtkSourceView, Gtk.Picture, hex)** | Read decoded smali, XML, images, binaries in-app |

**Vision:** open an APK → see raw contents immediately → optionally decode → **browse and read the decoded tree in the same window** without leaving the app or opening external tools.

Pass 3 implements the first two layers and most of the decode/cache path. The **tree browser + viewers + framework UI** layers are still absent, so the product does not yet match the diagram in methodology §2.

## 3. Full Decode vs the Files tab (raw ZIP entries)

### 3.1 What happens today

When you open an APK, `MainWindow.load_archive_entries()` calls `ApkArchive.list_entries(apk_path)` and fills a `Gtk.TreeView` with paths like `classes.dex`, `lib/arm64-v8a/…`, `META-INF/…`, `resources.arsc`. That is a **direct read of the APK as a ZIP archive** — fast, no Java, exactly what Phase 1 specified.

When you click **Full Decode**, `ApktoolRunner` runs Apktool, writes to a partial directory, renames it to the final cache key, and sets `session.cache_dir` and `DecodeState.DECODED`. The **Properties** tab can refresh from that folder (manifest metadata via `ApkMetadata.from_decode_dir`). The **Files** tab is **not** switched to the cache; it still shows the same raw ZIP list from `load_archive_entries()`.

### 3.2 Why that is a gap

An APK on disk is a **compressed package**. Full Decode produces a **project layout** Apktool understands:

```text
decoded/<cache-key>/
├── AndroidManifest.xml    ← decoded to text XML (not binary)
├── apktool.yml            ← decode metadata
├── smali/                 ← disassembled Dalvik (human-readable)
├── smali_classes2/        ← multi-dex
├── res/                   ← decoded resources (XML, PNG, …)
├── assets/
├── lib/
└── original/              ← copy of raw entries (Apktool convention)
```

Users who run Full Decode expect to **inspect smali and `res/`** — that is the main reason to decode. Today they must open `~/.cache/apk-manager/decoded/…` in a file manager or external editor. The methodology’s Phase 3–4 exit criterion is: **reopening a cached decode is useful inside the app**, not only on disk.

### 3.3 Intended behavior (not built yet)

After `DecodeState.DECODED` (and when `session.cache_dir` is valid), the Files tab (or a sibling tab) should:

1. Walk `session.cache_dir` on the filesystem (with the same path-safety rules as `ApkArchive.is_safe_archive_path`).
2. Populate a tree model with folders and files from the decode output.
3. Optionally offer a toggle: **Raw APK** vs **Decoded project** when both are available.

The continuation doc marks this as the **critical next milestone** (§5.1).

## 4. Decoded folder: `~/.cache/apk-manager/decoded/`

### 4.1 Location and purpose

ApkManager follows the [XDG Base Directory](https://specifications.freedesktop.org/basedir-spec/latest/) convention. `AppPaths.decoded_root` resolves to:

```text
~/.cache/apk-manager/decoded/
```

Each decode session gets a subdirectory named by a **cache key** (APK hash + Apktool version + decode options — see methodology §5.3). Example:

```text
~/.cache/apk-manager/decoded/a1b2c3…full/
```

Quick Manifest uses a lighter key (often `…-manifest`) and may only materialize manifest-related output; Full Decode fills the full tree.

### 4.2 Lifecycle

| Stage | Path | Notes |
|-------|------|-------|
| In progress | `decoded/<key>.partial-<pid>/` | Atomic write; removed or renamed on success |
| Success | `decoded/<key>/` | `session.cache_dir` points here |
| Invalidation | Key change | New APK hash, Apktool upgrade, or option change → new folder |

The cache **already exists and works** after decode. The gap is **UI wiring**: the app does not list or open files from this directory in the Files tab.

### 4.3 Related cache paths

| Path | Purpose |
|------|---------|
| `~/.cache/apk-manager/frameworks/` | Installed framework APKs for Apktool `-p` |
| `~/.cache/apk-manager/downloads/` | Get APKs temporary downloads |
| `~/.local/share/apk-manager/` | Session registry JSON, store install records |

## 5. GtkSourceView window (manifest / smali / XML)

### 5.1 What GtkSourceView is

[GtkSourceView](https://wiki.gnome.org/Projects/GtkSourceView) is a GTK widget that extends `Gtk.TextView` with:

- Syntax highlighting (language definitions for XML, YAML, etc.)
- Line numbers, margins, optional search
- Read-only mode suitable for inspectors

ApkManager already declares a **Meson dependency** on `gtksourceview-5` (see `README.md` and root `meson.build`), but **no window or embedded viewer uses it yet** (Phase 4: “dependency in Meson only”).

### 5.2 What files it would show

After decode, these paths are **text** (or text-like) and benefit from highlighting:

| Path pattern | Content |
|--------------|---------|
| `AndroidManifest.xml` | App manifest, permissions, components |
| `apktool.yml` | Apktool version, version info, compression flags |
| `res/**/*.xml` | Layouts, strings, drawables XML |
| `smali/**/*.smali` | Disassembled bytecode (Smali language) |
| `assets/**` (some) | Plain text configs |

Double-clicking (or a “Open” action) on a tree row would open a **read-only** GtkSourceView pane or secondary window — the pattern AppManager and many GNOME tools use for “view source.”

### 5.3 Why it matters

Without this, Full Decode’s value is mostly offline: users grep the cache in Vim or use external Smali tools. The unified methodology Phase 4 exit criterion is: **all decoded text content readable in-app**.

## 6. Hex and image viewers for decoded assets

### 6.1 Image viewer (`Gtk.Picture`)

Decoded `res/drawable*`, `res/mipmap*`, and many `assets/` files are **PNG, JPEG, WebP, or XML drawables**. For raster images, GTK 4’s `Gtk.Picture` (or the existing `ApkIcon` loading helpers) can display them inside the app.

Raw APK browsing already lists `resources.arsc` and binary XML; those are not directly viewable as images. **After decode**, `res/` contains extracted PNGs and **text XML** — the natural target for image + source viewers.

### 6.2 Hex viewer (bounded binary inspector)

Many entries remain binary: `.dex` (in `original/`), `.so` native libs, `.arsc`, compiled `.9.png`, `classes.dex`, etc. A **hex viewer** shows byte offsets and hex + ASCII columns for forensic inspection without executing code.

The methodology specifies **bounded** viewing (size limits, no loading multi-gigabyte game assets entirely into memory) — same spirit as `ApkArchive.read_entry()`’s 64 MiB cap for manifest reads.

### 6.3 Division of labor

| File type | Viewer |
|-----------|--------|
| `.smali`, `.xml`, `.yml` | GtkSourceView |
| `.png`, `.jpg`, `.webp` | Gtk.Picture |
| Other binary | Hex view (or “open externally”) |

None of these viewer paths are implemented in Pass 3; selecting a row in the Files tree does not open any content pane.

## 7. Framework install UI (`apktool if` / `lf` / `cf`)

### 7.1 What frameworks are

Some APKs (especially **system apps** or apps built against shared libraries) reference **framework resources** — typically `framework-res.apk` from an Android ROM. Apktool needs those installed locally to decode or rebuild correctly.

Apktool commands:

| CLI | Meaning |
|-----|---------|
| `apktool if <framework.apk>` | **I**nstall **f**ramework — import into local store |
| `apktool lf` | **L**ist **f**rameworks |
| `apktool cf <tag>` | **C**lear **f**ramework (remove one) |

### 7.2 What ApkManager already has

- `AppPaths.frameworks_dir` → `~/.cache/apk-manager/frameworks/`
- `ApktoolRunner` passes `-p <frameworks_dir>` on decode (methodology §5.2 JVM invocation)

So frameworks **on disk are used** if present. There is **no Preferences UI** to install, list, or remove them — users must run `apktool if` manually in a terminal.

### 7.3 What the UI would add (Phase 3)

- File picker: “Install framework APK…”
- List installed frameworks with tags/versions
- Remove selected framework
- When decode stderr mentions missing framework, show an **actionable banner** (“Install framework-res.apk from your device image”) — tied to continuation §5.2

This is separate from Get APKs; it is for **decode quality** on vendor/system APKs.

## 8. GSettings preference keys not fully wired

GSettings (`com.github.ApkManager`) stores user preferences in `~/.local/share/glib-2.0/schemas/`. Pass 3 **wired** keys like `install-path` and `remove-original-on-install`. Others appear in **Preferences UI and schema** but do not yet change application behavior.

### 8.1 `file-manager-icon-mode`

**Schema:** string, default `'android-logo'`.  
**Intent:** When APKs are installed to `~/Applications/android`, choose whether the file manager shows a **generic Android logo** or an **icon extracted from each APK** (via `.desktop` sidecar, extended attributes, or a companion icon file — exact mechanism TBD).

**Today:** Value is saved; install/rename logic does not create or update per-file icons in the file manager.

### 8.2 `runtime-engine`

**Schema:** string, default `'waydroid'`.  
**Intent:** Select which **Android runtime** launches an installed APK on Linux (e.g. [Waydroid](https://waydro.id/) container). This is **not** Java for Apktool — it is “run this Android app on desktop Linux,” which remains a hard problem (see [APK vs Linux runtime explanation](./20261007.explanation.apk.cannot.run.linux.java.runtime.grok-4.7.md)).

**Today:** Stored only; no “Run in Waydroid” action or integration.

### 8.3 `check-for-updates`

**Schema:** boolean, default `true`.  
**Intent:** Periodically or at startup, check whether a **newer ApkManager release** (or pinned Apktool JAR) exists and notify the user.

**Today:** Stored only; no network check or notification.

### 8.4 Other schema keys (partial wiring)

| Key | Wired? | Notes |
|-----|--------|-------|
| `decode-jobs` | Partial / verify | Should map to Apktool `-j`; confirm `ApktoolRunner` reads it |
| `java-heap-mb` | Partial / verify | Should map to `java -Xmx`; confirm runner |
| `preferred-repository` | Likely wired | Get APKs default store |
| `window-width` / `window-height` | May be unused | Window sizing persistence |

The continuation groups the first three under “preferences wiring” as **medium priority** (§5.3) — they do not block decoded browsing but affect polish and long-term UX.

## 9. How the gaps fit together (user journey)

```text
Today (Pass 3):
  Open APK → Files shows ZIP → Full Decode runs → cache on disk
                ↑                                    ↓
                └──────── Files still shows ZIP ─────┘
                Properties may show manifest metadata

Target (Phases 3–4):
  Open APK → Files shows ZIP (optional)
          → Full Decode → Files switches to decoded tree
          → Click AndroidManifest.xml → GtkSourceView
          → Click res/drawable/icon.png → Gtk.Picture
          → Click classes.dex → hex view
  Preferences → Install framework-res.apk → retry decode
  Preferences → file-manager icons / update checks / runtime (when implemented)
```
