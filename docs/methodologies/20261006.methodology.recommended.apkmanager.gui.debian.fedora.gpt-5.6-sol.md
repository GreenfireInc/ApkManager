## 1. Recommendation

Do not rewrite Apktool or add GUI code to its repository. Build **ApkManager** as a separate native Linux application:

- **Vala + GTK 4 + Libadwaita** for the interface.
- **Meson + Ninja** for builds, following AppManager.
- **libarchive** for an immediate, raw listing of the APK's ZIP entries.
- **A pinned Apktool release JAR** for decoded XML, resources, and smali.
- **`Gio.Subprocess`** to run Apktool without blocking the GTK main loop.
- **GtkSourceView 5** for read-only XML, YAML, and smali views.
- **XDG cache/data directories** for decoded output and recent-session metadata.

AppManager is the desktop-shell reference, not the APK engine. Apktool remains the engine.

### 1.1 Why this is preferable to JavaFX or Electron

| Choice | Recommendation | Reason |
|--------|----------------|--------|
| GTK 4 / Libadwaita / Vala | **Use** | Closest to AppManager, native Debian/Fedora integration, modest package size |
| JavaFX inside Apktool | Avoid | Creates an upstream fork and couples GUI releases to Apktool internals |
| Electron | Avoid for the first version | Larger runtime and weaker match to the requested AppManager design |
| Direct JNI/JVM embedding | Avoid initially | More lifecycle and crash complexity than a subprocess |
| Java sidecar service | Consider later | Useful only if repeated JVM startup or structured progress becomes a measured problem |

## 2. Product behavior

### 2.1 Opening an APK

The user can:

1. Double-click an `.apk` in Files, Dolphin, or another file manager.
2. Drag an APK into ApkManager.
3. Use **Open APK…**.
4. Run `apk-manager /path/to/application.apk`.

The application registers:

```ini
Exec=apk-manager %f
MimeType=application/vnd.android.package-archive;
```

The MIME type is already defined by Linux shared MIME information; ApkManager should not install a competing custom MIME definition.

### 2.2 Two-stage reading model

**Stage A — immediate raw inspection**

Open the APK as an untrusted ZIP archive with libarchive and display:

- Entry names, compressed/uncompressed sizes, and compression method.
- `classes.dex`, `classes2.dex`, and additional DEX files.
- Native ABIs inferred from `lib/<abi>/*.so`.
- `assets/`, `res/`, `META-INF/`, and signature-file presence.
- Previewable images and plain-text assets.

This works without Java and gives the user useful results immediately.

**Stage B — decoded inspection**

Run Apktool into a private cache directory to produce:

- Readable `AndroidManifest.xml`.
- `apktool.yml`.
- Decoded `res/` resources.
- Baksmali output under `smali/`, `smali_classes2/`, and later DEX directories.
- Copied assets, native libraries, originals, and unknown entries.

The user chooses either:

- **Quick manifest:** `apktool d --only-manifest -s`
- **Full decode:** `apktool d`

### 2.3 Main window

Use an `Adw.ApplicationWindow` containing an `Adw.NavigationSplitView`:

- **Sidebar:** recent APK sessions, package label, decode state, and last-opened time.
- **Tree pane:** raw or decoded file hierarchy.
- **Viewer pane:** manifest/details, source text, image preview, or bounded hex preview.
- **Header bar:** Open, Decode, Cancel, Export, APK Info, and search.
- **Bottom status area:** current decode phase and log disclosure.

### 2.4 Information window

Model it after AppManager's `AppImageInfoWindow`, using `Adw.PreferencesGroup` sections:

- **General:** package, application label, version name/code, APK SHA-256.
- **SDK:** minimum, target, and compile SDK when available.
- **Components:** activities, services, receivers, providers, launcher activity.
- **Permissions:** requested permissions from the decoded manifest.
- **Code:** DEX count and smali directory count.
- **Native:** included CPU ABIs and shared libraries.
- **Signing:** presence of v1 signature files only.
- **Files:** original path, APK size, decoded cache path, decoded size.

Do not claim that `META-INF/*.RSA` proves the APK is validly signed. Proper v2/v3/v4 verification requires Android's `apksigner` or equivalent and is a separate feature.

## 3. Runtime architecture

```text
File manager / drag-and-drop / file picker
                    |
                    v
        ApkManager Application (Vala)
          |                       |
          v                       v
  RawArchiveReader          ApktoolRunner
    (libarchive)           (Gio.Subprocess)
          |                       |
          v                       v
   immediate tree       Java 17+ + apktool.jar
                                  |
                                  v
                    XDG cache decoded directory
                                  |
                                  v
                     tree + viewers + APK info
```

### 3.2 Apktool command contract

Invoke Java with an argument vector, never a shell-composed command:

```text
java
-Xmx1024M
-Dfile.encoding=utf-8
-Djdk.util.zip.disableZip64ExtraFieldValidation=true
-Djdk.nio.zipfs.allowDotZipEntry=true
-jar
<libdir>/apk-manager/apktool.jar
d
-f
-j
<jobs>
-p
<cache>/apk-manager/frameworks
-o
<cache>/apk-manager/decoded/<sha256>
<apk-path>
```

Append `--only-manifest -s` for the quick pass.

The official Apktool release JAR contains its Linux `aapt2` resource for build operations. Read-only decoding does not require installing `aapt2` separately.

### 3.3 Progress and cancellation

Read Apktool output asynchronously and map known messages to phases:

- `Using Apktool …` → Starting
- `Baksmaling …` → Decoding code
- Manifest/resource messages → Decoding resources
- `Copying assets/lib …` → Copying files
- `Copying unknown files …` → Finishing

These are phases, not reliable percentages. Use an indeterminate progress bar with a phase label unless Apktool later exposes stable numerical progress.

Cancellation requirements:

1. Terminate the Java subprocess.
2. Wait for it to exit.
3. Mark the session cancelled.
4. Remove the incomplete temporary decode directory.
5. Rename a completed temporary directory atomically to its final cache path.

Decode to `<sha256>.partial-<pid>` first so a crash cannot leave a directory that looks complete.

## 4. Cache and state

Follow the XDG base-directory specification:

```text
$XDG_CACHE_HOME/apk-manager/decoded/<sha256>/
$XDG_CACHE_HOME/apk-manager/frameworks/
$XDG_DATA_HOME/apk-manager/sessions.json
$XDG_CONFIG_HOME/glib-2.0/settings/        # managed through GSettings
```

The cache key should include:

```text
SHA-256(APK bytes) + Apktool version + normalized decode options
```

Using only the APK hash would incorrectly reuse output after an Apktool upgrade or option change.

Store session metadata, not sensitive APK contents, in `sessions.json`. Use a versioned schema so it can be migrated later.

## 5. Security requirements

Treat every APK as hostile input.

1. **Never execute** code, scripts, native libraries, DEX files, or assets from the APK.
2. Pass subprocess arguments as an array; never interpolate the APK name into a shell command.
3. Resolve and verify every raw archive entry remains under its virtual root; reject absolute paths, `..`, NUL bytes, and unsafe links.
4. Do not follow symlinks while traversing decoded output.
5. Bound previews:
   - Text/hex preview maximum: configurable, default 2 MiB.
   - Image decoded-pixel limit to prevent decompression bombs.
   - Archive entry count and advertised uncompressed-size limits.
6. Decode only under ApkManager's cache root, never beside the original APK.
7. Use a private cache directory (`0700`) and private files by default.
8. Avoid automatic network access. Opening an APK must not fetch frameworks, metadata, icons, or updates.
9. Show Apktool errors as escaped text, not markup.
10. If Flatpak is used, grant selected-file access through the document portal and write only to app-owned storage.

Apktool has traversal tests and protections, but the GUI must still enforce its own containment at the archive and display layers.

## 6. Debian and Fedora dependencies

### 6.1 Debian/Ubuntu development host

```bash
sudo apt update
sudo apt install -y \
  valac meson ninja-build pkg-config \
  libgtk-4-dev libadwaita-1-dev \
  libglib2.0-dev libjson-glib-dev libgee-0.8-dev \
  libgtksourceview-5-dev libarchive-dev \
  desktop-file-utils default-jre-headless
```

### 6.2 Fedora development host

```bash
sudo dnf install -y \
  vala meson ninja-build pkgconf-pkg-config \
  gtk4-devel libadwaita-devel \
  glib2-devel json-glib-devel libgee-devel \
  gtksourceview5-devel libarchive-devel \
  desktop-file-utils java-latest-openjdk-headless
```

Package names should be confirmed on each supported release. The runtime requirement is **Java 17 or newer**, not one exact vendor package.

### 6.3 Debian compatibility decision

AppManager currently requires Libadwaita 1.6. ApkManager has two choices:

- Require Libadwaita 1.6 too, then support distributions that provide it and offer Flatpak/AppImage for older Debian.
- Avoid 1.6-only widgets and lower ApkManager's minimum after compiling and testing against Debian stable.

The second option provides broader native Debian support and is recommended unless a required widget proves otherwise. Do not copy AppManager's version floor mechanically.

## 7. Apktool distribution

`scripts/fetch-apktool.sh` should:

1. Pin an explicit Apktool release version.
2. Download the official release JAR over HTTPS.
3. Verify a committed SHA-256 value.
4. Place it in the Meson build staging directory.
5. Install it as `<libdir>/apk-manager/apktool.jar`.
6. Fail closed on checksum mismatch.

Do not silently download Apktool when ApkManager starts. Builds must be reproducible, and runtime must work offline.

Record the Apktool version and Apache-2.0 license in AppStream metadata and an in-app **About → Legal** section.

## 8. Implementation phases

### Phase 0 — Compatibility proof

- [ ] Decode representative APKs manually with the pinned JAR on Debian and Fedora.
- [ ] Test a normal APK, multi-dex APK, system/framework-dependent APK, malformed ZIP, and traversal fixture.
- [ ] Confirm minimum working GTK/Libadwaita versions on the chosen Debian baseline.

**Exit criterion:** documented support matrix and reproducible commands.

### Phase 1 — Native shell and raw browser

- [ ] Meson/Vala application using `HANDLES_OPEN | HANDLES_COMMAND_LINE`.
- [ ] File picker, drag-and-drop, and `.desktop` MIME registration.
- [ ] libarchive entry listing with containment and size checks.
- [ ] Text, image, and bounded hex viewers.

**Exit criterion:** useful APK inspection works without Java.

### Phase 2 — Apktool integration

- [ ] Check for Java 17+ and show an actionable warning if unavailable.
- [ ] Implement `ApktoolRunner` with async output and cancellation.
- [ ] Manifest-only quick decode and full decode.
- [ ] Atomic cache completion and cleanup of partial jobs.

**Exit criterion:** output matches manual Apktool decode and cancellation leaves no Java process.

### Phase 3 — Metadata and session UX

- [ ] Parse decoded manifest and `apktool.yml`.
- [ ] Add AppManager-style information window.
- [ ] Add recent-session registry and cache invalidation by tool version/options.
- [ ] Add framework install/list/clear controls using Apktool `if`, `lf`, and `cf`.

**Exit criterion:** reopening a cached APK is instant and metadata is consistent with decoded files.

### Phase 4 — Distribution

- [ ] Native Meson install.
- [ ] AppStream metadata and legal notices.
- [ ] `.deb` and `.rpm` packaging, or documented native dependency lists.
- [ ] Flatpak for systems whose native Libadwaita is below the selected minimum.
- [ ] Optional AppImage with a bundled minimal Java runtime.

**Exit criterion:** clean virtual machines can install, open, inspect, and uninstall ApkManager.

### Phase 5 — Optional features

- Signature verification through a separately packaged `apksigner`.
- JADX-based Java view.
- Compare two APKs.
- Export decoded output.
- Rebuild/sign workflow, clearly separated from read-only mode.

Do not include these in the MVP.

## 9. Testing plan

### Unit tests

- Archive path validation and size limits.
- Cache-key stability and invalidation.
- Apktool log-to-phase mapping.
- Manifest and `apktool.yml` metadata parsing.
- Java version parsing.

### Integration tests

- Open through `GApplication::open`.
- Quick and full decode using a fixed test APK.
- Cancel during smali and resource phases.
- Missing Java, unreadable APK, corrupt ZIP, missing framework, and full disk.
- Unicode, spaces, quotes, and leading dashes in APK file names.

### Distribution tests

- Build and run on the minimum supported Debian and Fedora releases.
- Install/uninstall desktop and MIME integration.
- Run offline.
- Verify no network request occurs while opening or decoding.
- Confirm no orphan Java process remains after cancel or application exit.

## 10. Definition of done

1. Double-clicking an APK opens ApkManager on supported Debian and Fedora systems.
2. The raw archive tree appears without Java.
3. With Java 17+, quick manifest and full decode complete successfully.
4. The manifest, resources, smali, images, and native-library inventory are readable in the GUI.
5. Malicious archive paths cannot escape app-owned storage.
6. Decode cancellation cleans up the child process and partial output.
7. Cache results are invalidated when the APK, Apktool version, or options change.
8. The app works offline after installation.
9. Legal metadata names bundled Apktool and any bundled Java runtime.
10. The first release remains read-only.
