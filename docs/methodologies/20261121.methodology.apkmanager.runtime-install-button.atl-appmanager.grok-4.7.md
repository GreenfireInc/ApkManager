## 1. What the button does

The install mark under each distro's copy button was a `Gtk.Image`. It is now a flat `Gtk.Button` with the same `system-software-install-symbolic` icon.

On the **Android Translation Layer** rows the click does three steps, in order:

1. Open GNOME Terminal and run that row's first line. That line is the package install: `sudo apt install curl libfuse2` on Debian, `sudo apt install curl libfuse2t64` on Ubuntu / Linux Mint, and `sudo dnf install curl fuse-libs` on Fedora. The window stays open until the user presses Enter, so they can read `apt` or `dnf`.
2. If that command exits 0 and `curl` is on `PATH`, download the AppImage from the URL already in the dialog into `~/Downloads/Android_Translation_Layer-3e686d14-anylinux-x86_64.AppImage` and mark it executable.
3. Run AppManager's `install` command on that file. AppManager moves it to `~/Applications` and writes the desktop entry.

The `curl`, `chmod`, and `./AppImage` lines still shown in the row are not typed into the terminal. The app does the download itself, and AppManager does the install. The terminal is only there because `sudo` needs one to ask for the password.

On the **Waydroid** and **Lepton** rows the same button opens a terminal and runs the commands printed on that row. Those rows are not AppImages, so AppManager is not involved.

## 2. How the terminal is started

This machine has GNOME Terminal 3.60 and no other terminal emulator. `gnome-terminal --help` documents `gnome-terminal [OPTION…] [-- COMMAND …]` and `--wait`. The button starts:

```text
gnome-terminal --wait -- bash -c <script>
```

`<script>` is the package line (or, for Waydroid and Lepton, the whole block), then a few lines that write the exit status to `/tmp/apk-manager-runtime-install.status`, print `Done.` or `The command failed`, and `read` until Enter.

`--wait` returns when the window closes. It does not return `dnf`'s exit code. The status file does. The script is one argument to `bash -c`, so a line such as `$(rpm -E %fedora)` in the Lepton block is still interpreted by bash, and the text is not passed through Vala's `printf`.

If the status file is missing, the click stops with "The terminal closed before the command finished." If the status is not `0`, the click stops with "The command failed" and does not download anything.

A toast names each step: opening the terminal, downloading, installing with AppManager. The button ignores further clicks until the sequence finishes.

## 3. How the download and AppManager are run

Both run as `GLib.Subprocess` on the GTK main loop (`communicate_utf8_async`), so the dialog stays responsive. `curl -fL --retry 3 --retry-delay 2 -o <dest> <url>` writes the file. A non-zero curl exit becomes a toast of curl's error text, cut at 180 characters.

AppManager is chosen in the order from the strategy:

| Check | Path |
|-------|------|
| Already installed | `~/Applications/AppManager` and executable. This machine matches (version 3.7.3) |
| On `PATH` | `app-manager` |
| Neither | Download `AppManager-3.8.0-anylinux-x86_64.AppImage` into `~/Downloads`, then run `<that file> install <that file>`, and use `~/Applications/AppManager` afterwards |

The ATL install is `<app-manager> install <path in ~/Downloads>`. AppManager's stdout, last line only, is the success toast (`Installed …`). Stderr is shown only when the exit code is not 0. AppManager's FUSE extraction progress uses carriage returns; the toast keeps the text after the last one.

`~/Downloads` is created if it is missing. The code does not run this from the Flatpak or the strict Snap. Those builds cannot see the host `dnf` or the host terminal. The `~/.local` install can.
