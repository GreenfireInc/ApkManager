## 1. Executive Summary

Converting Apktool into a GUI like AppManager means keeping Apktool exactly as it is — a Java decode engine — and building a native Linux shell around it.

- **Do not port** Apktool's smali/baksmali, resource-table, or binary-XML logic into Vala.
- **Do not embed** a Swing/JavaFX window inside Apktool; it would look foreign on GNOME and complicate Debian/Fedora packaging.
- **Do build** ApkManager as a Vala + GTK 4 + Libadwaita + Meson application that:
  1. Opens `.apk` files from the file manager, drag-and-drop, picker, or CLI.
  2. Lists raw APK contents instantly without Java (ZIP-level view).
  3. Runs a pinned `apktool.jar` as a background subprocess for decoded views.
  4. Caches decoded output under the XDG cache directory keyed by content hash.
  5. Presents manifest, resources, smali, assets, native libraries, and signatures in read-only viewers.

AppManager is the pattern for the desktop shell. Apktool is the engine.

## 2. What Each Upstream Project Contributes

### 2.1 Apktool (`Others/Apktool/`)

- CLI entry point: `brut.apktool.Main` (`d`/`decode`, `b`/`build`, `if`/`install-framework`, `lf`, `cf`, `empty-framework-dir`).
- Library: `brut.androlib.ApkDecoder` + `Config` (decode sources, resources, assets, framework directory, jobs, force).
- Logging: `brut.common.Log` over `java.util.logging`; phase lines such as `Baksmaling ...`, `Copying ...`, `Decoding ...` can drive GUI progress.
- Wrapper script: `scripts/linux/apktool` defines the canonical JVM flags (heap, file encoding, ZIP-64 validation flags).
- Release JARs bundle a Linux `aapt2` resource used on the **build** path; read-only decoding needs only a Java 17+ runtime plus the JAR.

### 2.2 AppManager (`Others/AppManager/`)

- Application lifecycle with `HANDLES_OPEN | HANDLES_COMMAND_LINE` and `open()` file routing.
- `DropWindow` for drag-and-drop open, `AppImageInfoWindow` with `Adw.PreferencesGroup` sections.
- Background work off the GTK main loop (`Thread`, `ThreadPool`, async subprocess patterns).
- Meson build with Libadwaita/GTK4/JSON/Gee dependencies.
- `.desktop` `Exec` + `MimeType` registration and AppStream metadata.

ApkManager copies these shell patterns, not APK logic (AppManager has none).

## 3. Recommended Architecture

```text
User opens .apk
  (double-click / drag-and-drop / picker / CLI)
        |
        v
ApkManager Application (Vala / GTK 4 / Libadwaita)
  |-- RawArchiveReader (libarchive, no Java)
  |     -> instant ZIP listing: DEX, lib/<abi>, assets, META-INF
  |
  |-- ApktoolRunner (Gio.Subprocess, async)
  |     -> java -jar apktool.jar d [--only-manifest -s] [-f] [-j N]
  |     -> XDG cache output, phase telemetry, cancellation
  |
  |-- DecodeSessionRegistry (JSON index)
  |-- MainWindow (sessions + tree + viewers)
  |-- ApkInfoWindow (package / SDK / permissions / components)
  |-- Viewers (GtkSourceView / Gtk.Picture / bounded hex)
```

### Why subprocess first

| Approach | Verdict |
|---|---|
| Vala shell + `java -jar apktool.jar` subprocess | **Use for v1** — no Apktool fork, clean crash isolation, easy upgrades |
| Long-lived Java sidecar using `apktool-lib` | Defer until JVM startup or progress becomes a measured bottleneck |
| JNI / in-process JVM embedding | Avoid — crash and lifecycle complexity |
| JavaFX GUI inside Apktool repo | Avoid — forks upstream, poor GNOME integration |
| Electron wrapper | Avoid for this request — heavier than the AppManager pattern |

## 4. Backend Integration Contract

### 4.1 Pinned engine

- `scripts/fetch-apktool.sh` pins one Apktool release, downloads the official JAR over HTTPS, verifies SHA-256, and installs it to `<libdir>/apk-manager/apktool.jar`.
- Never download Apktool at GUI startup; the app must work offline after install.
- Record Apktool version + Apache-2.0 license in AppStream metadata and About → Legal.

### 4.2 JVM command (argument vector, never shell string)

```text
java
-Xmx1024M
-Dfile.encoding=utf-8
-Djdk.util.zip.disableZip64ExtraFieldValidation=true
-Djdk.nio.zipfs.allowDotZipEntry=true
-jar
<libdir>/apk-manager/apktool.jar
d
-f
-j <jobs>
-p <cache>/apk-manager/frameworks
-o <cache>/apk-manager/decoded/<key>.partial-<pid>
<apk-path>
```

Add `-s --only-manifest` for the fast metadata pass. Decode to a `.partial-<pid>` directory, then atomically rename to the final cache path only on exit code 0.

### 4.3 Cache key

```text
key = SHA-256(APK bytes) + Apktool version + normalized decode options
```

APK hash alone is insufficient; tool upgrades and option changes must invalidate the cache.

### 4.4 Progress mapping

Parse Apktool stdout asynchronously; treat lines as phases, not percentages:

| Apktool output | GUI phase |
|---|---|
| `Using Apktool ...` | Starting |
| `Baksmaling ...` | Decoding code |
| Manifest / resource decode lines | Decoding resources |
| `Copying assets ...` / `Copying lib ...` | Copying files |
| `Copying unknown files ...` | Finishing |

Use an indeterminate progress bar with a phase label plus an expandable log view.

### 4.5 Cancellation and cleanup

1. Cancel the `Cancellable` and force-exit the Java subprocess.
2. Wait for process exit; confirm no `apktool.jar` child remains.
3. Mark session cancelled and delete the `.partial-<pid>` directory.
4. Never leave a directory that looks complete but is not.

## 5. Reading Pipeline

### Stage A — Instant raw view (no Java)

Using libarchive, show entry name, sizes, compression, plus derived facts:

- DEX files (`classes.dex`, `classes2.dex`, ...).
- Native ABIs from `lib/<abi>/*.so`.
- `assets/`, `res/`, `META-INF/*.RSA|*.SF|*.MF` presence.
- Previewable images and plain-text assets.

Gate: raw listing works with no Java installed.

### Stage B — Fast manifest pass

Run `apktool d -s --only-manifest` to produce readable `AndroidManifest.xml` + `apktool.yml` in ~1 second for typical APKs. Feed the info window: package, version, SDK levels, permissions, components, launcher activity.

### Stage C — Full decode

Run full `apktool d` for `res/`, `smali*/`, assets, libs, originals, and unknown files. Browse in a tree with:

- `GtkSourceView`, read-only: XML, YAML, smali (plain text initially).
- `Gtk.Picture`: PNG/JPEG/WebP.
- Bounded hex + Open With: `.so`, `.dex`, `resources.arsc`, unknown binaries (default 2 MiB cap).

## 6. Framework APK Handling

System/vendor APKs may require framework resources. ApkManager should:

- Keep frameworks under `<cache>/apk-manager/frameworks` and pass `-p` on every decode.
- Map Apktool's framework-not-found error to an in-app banner with **Install framework…**.
- Wrap `apktool if` (install), `lf` (list), and `cf` (clean) in Preferences.
- Never fetch frameworks automatically on APK open; explicit user action only.

## 7. Debian & Fedora Dependencies

Runtime requirement is **Java 17 or newer**, not one exact vendor package. Verify package names on each supported release.

### 7.1 Debian / Ubuntu development host

```bash
sudo apt update
sudo apt install -y \
  valac meson ninja-build pkg-config \
  libgtk-4-dev libadwaita-1-dev libgtksourceview-5-dev \
  libglib2.0-dev libjson-glib-dev libgee-0.8-dev \
  libarchive-dev desktop-file-utils \
  default-jre-headless git curl
```

### 7.2 Fedora development host

```bash
sudo dnf install -y \
  vala meson ninja-build pkgconf-pkg-config \
  gtk4-devel libadwaita-devel gtksourceview5-devel \
  glib2-devel json-glib-devel libgee-devel \

  java-latest-openjdk-headless git curl
```

### 7.3 Desktop integration

```ini
Exec=apk-manager %f
MimeType=application/vnd.android.package-archive;
```

`application/vnd.android.package-archive` is already defined by shared MIME info on both distros; install a custom MIME XML only if a conflict is proven.

### 7.4 Libadwaita compatibility note

If ApkManager requires Libadwaita 1.6 (like AppManager), Debian 13+ and current Fedora are native targets; Debian 12 needs Flatpak (`org.gnome.Platform` + OpenJDK extension) or a lowered widget minimum. Confirm the minimum by compiling against Debian stable before locking it in.

```bash
./scripts/fetch-apktool.sh
meson setup build --prefix=$HOME/.local
meson compile -C build
meson install -C build
update-desktop-database ~/.local/share/applications
```

| Format | Java | Apktool | Use |
|---|---|---|---|
| Native install / `.deb` / `.rpm` | Distro default headless JRE dependency | Bundled JAR under app libdir | Normal distro installs |
| Flatpak | OpenJDK SDK extension | Bundled | Older Debian / sandboxed installs |
| AppImage | Bundled minimal JRE (`jlink`) | Bundled | Portable release matching AppManager's format |

## 9. Security Boundaries (Read-Only v1)

1. Treat every APK as hostile; never execute DEX, `.so`, scripts, or assets.
2. Never interpolate file paths into a shell command; use argv arrays.
3. Reject absolute paths, `..`, NUL bytes, and unsafe links in archive entries; contain everything under the app cache root.
4. Do not follow symlinks when traversing decoded output.
5. Bound previews (text/hex size, image pixels, entry count, uncompressed size).
6. Private cache默认 `0700`; no network access on open/decode.
7. Render Apktool errors as escaped text, not markup.
8. Keep the first release read-only: no `apktool b`, no signing, no device install.

## 10. Acceptance Checklist

1. [ ] Double-clicking an APK opens ApkManager on supported Debian and Fedora systems.
2. [ ] Raw ZIP listing appears without Java installed.
3. [ ] Fast manifest pass fills package/SDK/permissions within seconds for a typical APK.
4. [ ] Full decode output matches manual `apktool d` with the same pinned JAR.
5. [ ] Cancel terminates the Java child and removes partial output.
6. [ ] Reopening a cached APK is instant; tool/option changes invalidate correctly.
7. [ ] Framework-dependent APKs surface an actionable install-framework flow.
8. [ ] App works offline; opening/decoding performs no network access.
9. [ ] No orphan Java processes remain after cancel or app exit.
10. [ ] First release remains read-only.
