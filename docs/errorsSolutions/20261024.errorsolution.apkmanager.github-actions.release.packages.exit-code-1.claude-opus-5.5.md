## 1. What you see

Runs of **Release packages** for `main` (PR #21 merge `97a1c8b`), tag `v0.2.0` and tag `v0.2.1` all fail. **CI / Compile (Ubuntu)** passes; every packaging job fails; **Publish GitHub Release** is skipped because it depends on all five.

The GitHub API (public, no login) shows where each job stopped:

| Job | Failing step |
|-----|--------------|
| Debian (.deb) | 4 — Build .deb |
| RPM (.rpm) | 5 — Build source tarball and RPM |
| Flatpak | 4 — Build Flatpak bundle |
| Snap | 3 — Build snap (`snapcore/action-build`, runs snapcraft through `sudo`) |
| AppImage | 4 — Install AppImage tools |

The annotation text (“Process completed with exit code 1”) only says *that* a shell step failed. Full logs need an authenticated `gh run view --log-failed`, so each job was reproduced locally from a clean copy of the committed tree instead.

## 2. What it means — five different root causes

These packaging jobs had never run successfully: before the previous fix, `release.yml` only ran on `v*` tags, and none had been pushed. Each format had its own latent bug.

### 2.1 Debian — checking for a command that does not exist

`scripts/build-packages.sh` guarded the deb build with `need debhelper`, i.e. `command -v debhelper`. The **debhelper** package installs `dh`, `dh_auto_build`, … but no `debhelper` executable, so the check always failed:

```text
Missing required tool for this target: debhelper
```

### 2.2 RPM — a system cache file shipped as a package file

`data/meson.build` compiled the GSettings schema and **installed** the result:

```text
/usr/share/glib-2.0/schemas/gschemas.compiled
```

That file is a cache shared by every application on the system and is regenerated on the target machine. It is not in the spec's `%files` list, and `rpmbuild` treats any installed-but-unlisted file as fatal (“Installed (but unpackaged) file(s) found”). The `.deb` built anyway but also shipped the file, which can clash with other packages.

### 2.3 Flatpak — three problems in sequence

| # | Error | Meaning |
|---|-------|---------|
| a | `curl: (6) Could not resolve host: bitbucket.org` | Flatpak builds have **no network**. `scripts/fetch-apktool.sh` downloads `apktool.jar` during `meson compile`. |
| b | `Error moving file …/com.github.ApkManager.desktop: File exists` | `rename-desktop-file` / `rename-icon` renamed the files to the name they already had. |
| c | `… com.github.ApkManager.svg is not a valid icon: Expected a square icon but got: 294x345` | Flatpak export requires square app icons; `public/assets/icons/operatingSystems/android.svg` had a 294×345 viewBox. |

### 2.4 Snap — wrong base, and the source was outside the project

Two independent problems:

1. **`base: core22`** uses the GNOME 42 SDK (GTK 4.6, **libadwaita 1.1**). ApkManager uses `Adw.Dialog`, `Adw.ToolbarView`, etc. from libadwaita **1.5**, so it can never compile on core22.
2. **Project directory.** The workflow ran snapcraft with `path: build/snap`. Snapcraft builds inside a container that only contains the project directory, but the meson part used `source: ../..` — the repository root, outside that directory — so the sources were unreachable.

### 2.5 AppImage — no FUSE on the runner

`linuxdeploy` and `appimagetool` are themselves AppImages. Running an AppImage normally mounts it with **FUSE 2** (`libfuse2`), which GitHub's `ubuntu-24.04` image does not install. The tool-install script's self-check (`linuxdeploy --help`) therefore failed. The script also downloaded `appimagetool` from the retired AppImageKit repository (a 2023 build).

A related local-only bug surfaced while testing: when the build is launched from a terminal that itself runs inside an AppImage (Cursor), `OWD` is set and `appimagetool` writes the result into `$OWD` (the repository root) instead of `build/`. The script then did not find it and built the AppImage a second time.

### 2.6 Node.js 20 warnings (not failures)

GitHub removed Node 20 from runners in September 2026 and now forces JavaScript actions onto Node 24, warning for every action whose `action.yml` still says `node20`: `actions/checkout@v4`, `actions/upload-artifact@v4`, `actions/download-artifact@v4`, `softprops/action-gh-release@v2`, and `snapcore/action-build@v1`. They still run today, but are unsupported.

## 3. Fix

### 3.1 Debian

```bash
# scripts/build-packages.sh
need dh        # was: need debhelper
```

### 3.2 RPM (and Debian hygiene)

`data/meson.build`: the `gschemas.compiled` custom target is now **build-tree only** (`build_by_default: true`, no `install:`). `gnome.post_install(glib_compile_schemas: true)` still regenerates the system cache on a plain `meson install` and correctly skips it under `DESTDIR` (package builds); distro triggers handle it for installed packages.

### 3.3 Flatpak

| Change | File |
|--------|------|
| Apktool 2.9.3 declared as a checksummed `file` source (`sha256: 7956eb04…46f4`) placed at `third_party/apktool/apktool_2.9.3.jar` | `packaging/flatpak/com.github.ApkManager.yml` |
| `fetch-apktool.sh` takes the source root as a second argument and copies that vendored JAR when present, downloading only otherwise | `scripts/fetch-apktool.sh`, `meson.build` |
| `skip: [.git, .flatpak-builder, build, dist]` on the `dir` source, so build output is not copied back into the sandbox | Flatpak manifest |
| Removed the self-renaming `rename-desktop-file` / `rename-icon` | Flatpak manifest |
| Square icon: `viewBox="-172.5 -70 345 345"` (artwork unchanged, centered) | `public/assets/icons/operatingSystems/android.svg` |
| `/third_party/apktool/` ignored | `.gitignore` |

### 3.4 Snap

`build/snap/snapcraft.yaml`:

- `base: core24` (GNOME 46: GTK 4.14, libadwaita 1.5 — the same versions the developer host builds against).
- `platforms:` instead of core22's `architectures:`.
- Paths are now relative to the **repository root**: `source: .` for meson, `source: build/snap/local/bin` for the launcher.
- `--libdir=lib` so `apktool.jar` lands in `/usr/lib/apk-manager`, matching the snap `layout`.
- Stage `libgee-0.8-2` and `libarchive13t64`, which the GNOME runtime does not provide.

Snapcraft only finds `snap/snapcraft.yaml` at the project root, so — exactly like `debian/` → `build/debian` — the build creates a temporary symlink `snap` → `build/snap` at the repository root:

- `scripts/build-packages.sh snap`: `link_snap_dir` / `unlink_snap_dir`, then `snapcraft pack --output dist/…`.
- `release.yml`: installs Snapcraft and runs `sudo snapcraft pack --destructive-mode`. The runner is Ubuntu 24.04, which matches core24, so no LXD container (and no Node 20 `snapcore/action-build`) is needed.
- `/snap` ignored in `.gitignore`.

### 3.5 AppImage

- `APPIMAGE_EXTRACT_AND_RUN=1` in `.github/scripts/install-appimage-tools.sh` and `packaging/appimage/build-appimage.sh`, so AppImage tools extract themselves instead of needing FUSE.
- `appimagetool` downloaded from the maintained `AppImage/appimagetool` repository.
- `build-appimage.sh` unsets `OWD` and sets `LDAI_OUTPUT` to the final `dist/ApkManager-<version>-<arch>.AppImage` path.

### 3.6 Node 24 action versions

| Action | Before | After |
|--------|--------|-------|
| `actions/checkout` | `@v4` | `@v6` |
| `actions/upload-artifact` | `@v4` | `@v7` |
| `actions/download-artifact` | `@v4` | `@v8` |
| `softprops/action-gh-release` | `@v2` | `@v3` |
| `snapcore/action-build` | `@v1` | removed (no Node 24 release; replaced by shell steps) |

## 5. How to confirm on GitHub

1. Commit these changes on a `CS.*` branch, open a PR into `main` (CI runs), merge.
2. **Actions → Release packages** runs for `main`: all five package jobs should be green, with artifacts attached to the run.
3. For a public release, push a new tag (for example `v0.2.2`). Existing tags `v0.2.0` / `v0.2.1` point at commits without these fixes; re-running them will fail the same way.

If a job still fails, `gh run view <run-id> --log-failed` (requires `gh auth login`) shows the exact log lines.
