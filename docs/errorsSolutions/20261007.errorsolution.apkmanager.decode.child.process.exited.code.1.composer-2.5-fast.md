## 1. What the message means

`Child process exited with code 1` is **not** an ApkManager or GTK error string. It is the text GLib attaches to `Gio.Subprocess.wait_check()` when a child program finishes with a **non-zero status**.

| Piece | Meaning |
|-------|---------|
| Child process | The `java -jar apktool.jar d …` process started by `ApktoolRunner` |
| Exited | Java actually finished (it was not killed by a signal) |
| Code 1 | Apktool (or the JVM) reported failure. Unix convention: 0 is success, 1 is a general error |

Opening an APK only lists ZIP entries with libarchive and does not start Java. This status line appears when **Quick Manifest** or **Full Decode** runs. Both buttons were failing for every APK, so the message showed up as soon as decode started after a file was loaded.

The useful detail was thrown away. Apktool prints the real reason on stderr (`Unrecognized option: -j`). The runner read stdout only, then displayed GLib’s generic `e.message` from `wait_check_async`.

## 2. Why Apktool exited 1

Pinned Apktool **2.9.3** accepts:

```text
apktool d -f -o <dir> -p <frameworks> [-s] [-r] [--force-manifest] <apk>
```

It does **not** implement:

| Flag the GUI sent | Apktool’s response |
|-------------------|--------------------|
| `-j <jobs>` | `Unrecognized option: -j` then exit 1 |
| `--only-manifest` | `Unrecognized option: --only-manifest` then exit 1 |

Those flags exist in later Apktool releases and in the methodology docs. The JAR downloaded by `scripts/fetch-apktool.sh` is 2.9.3. Confirmed on this host:

```text
$ java -jar ~/.local/lib64/apk-manager/apktool.jar
Apktool 2.9.3
…
usage: apktool d[ecode] [options] <file_apk>
 -f,--force
 -o,--output <dir>
 -p,--frame-path <dir>
 -r,--no-res
 -s,--no-src
 -t,--frame-tag <tag>
```

`ApktoolRunner` always appended `-j`. **Full Decode** therefore failed before reading the APK. **Quick Manifest** also appended `--only-manifest`, so that path failed the same way.

Advanced options that *are* in 2.9.3 (hidden unless you pass `-advance`) include `--force-manifest`: decode `AndroidManifest.xml` even when resource decoding is off. That is the 2.9.3 stand-in for `--only-manifest`.

## 3. Fix applied

### 3.1 Command line (`src/core/apktool_runner.vala`)

Full decode:

```text
java -Xmx1024M … -jar apktool.jar d -f -p <frameworks> -o <dir> <apk>
```

Quick manifest:

```text
java … -jar apktool.jar d -f -p <frameworks> -s -r --force-manifest -o <dir> <apk>
```

| Flag | Role |
|------|------|
| `-s` | Do not baksmali (`--no-src`) |
| `-r` | Do not decode resources (`--no-res`) |
| `--force-manifest` | Still decode the compiled manifest |

`-j` and `--only-manifest` are no longer passed. The `jobs` argument was removed from `decode_async` because 2.9.3 has nothing to pass it to. `DEFAULT_DECODE_JOBS` remains in `app_constants.vala` for a future Apktool pin that supports `--jobs`.

Verified against the installed JAR: both flag sets get past CLI parsing (`I: Using Apktool 2.9.3 on …`). A deliberately invalid dummy APK then fails inside the decoder, which is a different error and is expected.

### 3.2 Show Apktool’s text instead of GLib’s

The subprocess is started with `STDOUT_PIPE | STDERR_MERGE`, so stderr is read on the same stream (this also avoids a stderr-pipe deadlock). On a non-zero exit the status line prefers, in order:

1. `Unrecognized option: …`
2. The Java exception line, plus `Caused by:` when present
3. The last Apktool output line
4. GLib’s `Child process exited with code N` only if Apktool printed nothing

The status label wraps so a long exception is visible.

## 4. What you should run

The rebuilt binary is already installed to `~/.local/bin/apk-manager` from this fix. If you build again yourself:

```bash
cd /home/corey/Workspace/Applications/ApkManager
meson compile -C build
meson install -C build
export PATH="$HOME/.local/bin:$PATH"
apk-manager /path/to/app.apk
```

Then use **Quick Manifest** or **Full Decode**. A valid APK should get past option parsing. If Apktool still cannot decode that file (corrupt manifest, missing framework, and so on), the status line should quote Apktool’s exception instead of only `Child process exited with code 1`.
