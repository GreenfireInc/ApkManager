## Summary

There were three separate failures in that output, and only the first one was real:

1. **The build ran out of disk space.** `.x86_scripts/build-all.sh` starts by building the `lepton-builder` Podman image. Rootless Podman stores images under `~/.local/share/containers/storage`, which is on `/home`. At the time, `/home` had **5.2 GB free out of 1.8 TB (100% used)**. The lepton-x86 project says a full build needs **more than 100 GB** and several hours (it compiles an Android 11 system image from AOSP source). It failed while writing the very first image layer.
2. **`tar … Cannot open`** happened because the terminal kept going after the build failed. The tarball it tried to unpack is the build's output, and it was never produced.
3. **`sudo: …/setup-host.sh: command not found`** came from the same cause: nothing was unpacked, so the script didn't exist. (`~/.local/share/Steam/compatibilitytools.d` didn't exist either, so `tar -C` would have failed even with a tarball.)

## Root causes in ApkManager

| Problem | Effect |
|---------|--------|
| The Lepton commands built lepton-x86 from source | Needs 100+ GB of disk and hours of compile time, even though the project publishes ready-made release tarballs |
| `open_terminal_script` ran the lines as a plain `bash -c` script with no `set -e` | A failed step didn't stop the script; later steps ran on missing files and buried the real error under follow-on errors. The final status was that of the last command, not the first failure |
| The terminal inherited ApkManager's working directory | `git clone` landed inside the ApkManager repository (`apkManager/lepton-x86/`, untracked, 23 MB) because the app was started from there |
| No `mkdir -p` before `tar -C ~/.local/share/Steam/compatibilitytools.d/` | That folder only exists after Steam has been run once |
| Ubuntu / Linux Mint ran `sudo add-apt-repository multiverse` unconditionally | On Mint, `add-apt-repository` comes from `mintsources` and only understands `ppa:` lines. It would write the bare word `multiverse` into a sources file and break `apt update`. Mint already has multiverse enabled |

## Solution

### 1. Install the prebuilt release instead of building

lepton-x86 publishes `lepton-x86_64-v3.0.2-x86_64.4.tar.zst` (598 MB download, 1.52 GB unpacked). It is exactly what `build-all.sh` would produce: a single `lepton-x86_64/` directory with the tool, the Android rootfs, the system bake, `compatibilitytool.vdf` and `setup-host.sh`. All three distributions now share one block, `LEPTON_X86_STEPS`:

```bash
# x86_64: install the community port's prebuilt release
curl -fL --create-dirs -o ~/Downloads/lepton-x86_64-v3.0.2-x86_64.4.tar.zst "https://github.com/Lolig4/lepton-x86/releases/download/v3.0.2-x86_64.4/lepton-x86_64-v3.0.2-x86_64.4.tar.zst"
mkdir -p ~/.local/share/Steam/compatibilitytools.d
tar --zstd --xattrs -xf ~/Downloads/lepton-x86_64-v3.0.2-x86_64.4.tar.zst -C ~/.local/share/Steam/compatibilitytools.d/
~/.local/share/Steam/compatibilitytools.d/lepton-x86_64/setup-host.sh
```

- `setup-host.sh` elevates itself with `sudo`, so it's run as the user, as the upstream packaging script prints.
- `curl` and `zstd` were added to each distribution's package line, since `tar --zstd` needs the `zstd` binary.
- The Requirements text now says the prebuilt release needs about 3 GB, and building it yourself needs more than 100 GB.

### 2. Stop at the first failure, from the home folder

`open_terminal_script` now wraps the commands like this before handing them to `gnome-terminal`:

```bash
cd ~
(
set -eo pipefail
<commands shown in the dialog>
)
status=$?
```

- `set -e` stops at the first failing line, so a failed download can no longer be followed by `tar` and `setup-host.sh` errors. The status written for the app is now the first failure's.
- `pipefail` also catches failures on the left of a pipe, such as `curl -s https://repo.waydro.id | sudo bash` on the Waydroid page.
- The subshell keeps the "The command failed (N). Press Enter to close." footer working after a failure.
- `cd ~` keeps downloads and clones out of whatever folder ApkManager was launched from.

This applies to every runtime on the dialog, not just Lepton.

### 3. Check disk space before opening the terminal

For Lepton, `run_install` calls the new `require_free_space(LEPTON_FREE_BYTES)` first. It queries free space on the home filesystem, and if less than 3 GB is available, shows a toast such as "Not enough disk space: 2.1 GB free in your home folder, 3.2 GB needed." instead of opening the terminal.

### 4. Only add multiverse where it's missing

The Ubuntu / Linux Mint commands now start with:

```bash
# Ubuntu: enable multiverse (already on in Linux Mint)
grep -rqs multiverse /etc/apt/sources.list /etc/apt/sources.list.d/ || sudo add-apt-repository -y multiverse
```

### 5. Cleanup of the failed run

- Deleted the stray `lepton-x86/` clone from the ApkManager repository root.
- Removed the dangling Podman image left by the aborted build (`podman image prune -f`).

## If it still fails

- **Disk space toast:** free up space on `/home`. `df -h ~` shows what is available; `podman system prune` removes unused Podman data.
- **Steam not installed yet:** the commands install `steam-installer` (Debian/Ubuntu) or `steam` (Fedora). Run Steam once, then restart it after the install so it lists **Lepton (x86_64)** as a compatibility tool.
- **GPU:** the x86_64 port currently supports AMD GPUs only. On other GPUs, set `LEPTON_FORCE_SOFTWARE=true` in `~/.local/share/Steam/compatibilitytools.d/lepton-x86_64/lepton.conf`.
- **Newer release:** update the version in `LEPTON_X86_STEPS` in `runtime_install_dialog.vala` (URL and both filenames).
- **Building from source anyway:** follow the lepton-x86 README on a disk with more than 100 GB free.
