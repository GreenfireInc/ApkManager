## Short answer

Yes, and more than one. Lepton has no single "verbose mode" switch like ATL's
`ANDROID_LOG_TAGS=*:v -X -verbose:jni`. It does have:

1. a **launcher log file** that every run writes automatically;
2. **`lepton logcat`**, a live stream of Android's own log, which is the closest
   match to what ApkManager's Debug page shows for ATL;
3. **automatic logcat dumps** to files when an app dies in its first 30 seconds,
   or on every run with `LEPTON_DUMP_LOGCAT=1`;
4. heavier developer tools: `LEPTON_DEBUG` (shell trace), `LEPTON_STRACE`,
   gdb/lldb servers, Perfetto traces, bootchart, and `collect_logs`.

The difference that matters for ApkManager: ATL is **one process**, and its
Android log comes out on that process's stdout and stderr, so ApkManager just
reads the pipes. Lepton runs Android **inside a Podman container**. The
launcher's stdout only carries Lepton's own progress messages; the app's log
lives in the container's `logcat` buffers, so it has to be fetched with a
second command while the container is running.

## What ApkManager's ATL debug does today

For comparison, the Debug button runs:

```text
ANDROID_LOG_TAGS=*:v  [GDK_DEBUG=gl-egl on X11]
android-translation-layer <apk> -X -verbose:jni
```

and reads stdout and stderr line by line (`RuntimeRunner.start_atl_debug`).
Every line is kept for **Save JSON**; lines matching `atl_debug_error`
(exception, error, fatal, caused by, UnsatisfiedLink, cannot locate symbol,
NoSuch…, NoClass…) are shown on the page.

## Lepton's debug facilities

### 1. Launcher log file (always on)

Every `start` / `waitforexitandrun` calls `log_to_file`, which tees the
launcher's stdout and stderr into:

```text
${STEAMVR_LOGS_DIR}/lepton-<context>.log
```

On SteamOS `STEAMVR_LOGS_DIR` comes from `steamvr logpath`. On a desktop
without SteamVR (this machine), the port falls back to:

```text
~/.local/share/lepton/logs/lepton-<context>.log
```

ApkManager's runs use context `steamlaunch-<SteamAppId>`, where the app id is
the hash ApkManager computes from the package name. Files already on this
machine:

```text
~/.local/share/lepton/logs/lepton-steamlaunch-2824592663.log
~/.local/share/lepton/logs/lepton-steamlaunch-test-lepton.log
```

Each run starts with a header, then Lepton's own progress. The last test run
transcribed from that file:

```text
Lepton v3.0.2-12-gcd0c6e8 (rootfs <unknown version>) starting up at Sat Nov 21 08:27:41 PM EST 2026
Setting APP_PATH to ~/Downloads/Firefox/uptodown-com.zeptolab.bulletecho.google.apk
APP ID: com.uptodown
ACTIVITY NAME: com.uptodown.activities.MainActivity
APP VERSION: 740
MIN SDK VERSION: 23
Clearing baked app data due to app or depot changed
ERROR: Unable to find layer for 'libVkLayer_fossilize.so'
 -> Continuing without fossilize (no Steam shader pipeline capture)
Setting up overlays
Launching lepton-steamlaunch-test-lepton
Waiting for boot...
Error: pasta failed with exit code 1:
Port forwarding mode 'none' conflicts with previous mode
```

This is **not** the Android log. It shows container setup, install, and launch
failures, which is where Lepton problems on this machine have been so far.
ApkManager already captures the same text from the launcher's pipes when a run
fails, and shows it in the error dialog.

`lepton logsetup <context>` just runs `tail -f -n +1` on this file.

### 2. `lepton logcat` (closest to ATL's debug output)

```bash
~/.local/share/Steam/compatibilitytools.d/lepton-x86_64/lepton logcat steamlaunch-<id> [--full] [logcat args…]
```

`logcat_container` runs `podman exec … logcat -v threadtime,color` inside the
running container. By default it filters to the app's process
(`--pid=$(guess_app_pid)`); `--full` gives the whole system log. Extra
arguments go straight to Android's `logcat`, so the usual filters work, for
example `*:E` for errors only, or `-b crash` for the crash buffer.

Lepton sets `ro.logd.filter=disable` and a logcat buffer of
`LEPTON_LOGCAT_BUFFER_SIZE` (default `256K`), so nothing is filtered out by
default. That is the same idea as ATL's `ANDROID_LOG_TAGS=*:v`.

The catch: it only works **while the container is running**. Once the app
exits, `lepton` tears the container down and the buffers are gone, apart from
the dumps in the next section.

### 3. Logcat dumps to files

On teardown, `lepton.bin` calls `dump_logcat`. It writes the `main`, `system`,
`kernel`, `crash` and `radio` buffers to:

```text
${STEAMVR_LOGS_DIR}/lepton-logcats/<context>/logcat-<buffer>.log
```

That is `~/.local/share/lepton/logs/lepton-logcats/steamlaunch-<id>/` here.
This happens:

- **automatically** if the app exits within 30 seconds without ever showing a
  window (`EARLY_SHUTDOWN`). That is the crash-on-start case. It also clears the
  baked app data, so the next start reinstalls the app;
- **on every run** when `LEPTON_DUMP_LOGCAT` is set to any non-empty value.
  With it set, Lepton also writes its own timeline markers
  (`launch-request`, `post-setup`, `pre-start-container`, `post-start-container`,
  `killed`) into `logcat-lepton.log` in the same folder.

No `lepton-logcats` folder exists on this machine yet: every run so far failed
before Android booted (setpgid, Podman 4, pasta), so there was never a live
container to dump.

### 4. Developer switches and verbs

| Switch / verb | What it does | Notes for ApkManager |
|---------------|--------------|----------------------|
| `LEPTON_DEBUG=1` | `set -x` on `lepton.bin`: every shell command it runs is printed | Useful for launcher failures; very noisy |
| `LEPTON_STRACE=1` (`LEPTON_STRACE_ARGS`) | Starts the app under a debugger wait, then `strace -f` on it; the trace is copied to `lepton-logcats/<context>/strace-<package>.log` | Needs strace in the image; slows the app a lot |
| `LEPTON_DEBUG_LAUNCH=1` | App waits for a debugger (`am set-debug-app -w`) | Only useful with the gdb/lldb verbs |
| `gdb_server`, `lldb_server`, `gdb_attach`, `lldb_attach` | gdbserver64 / lldb inside the container | `gdb_attach` uses `sudo nsenter`; native debugging, not log output |
| `perfetto [context] [config]` | System trace to `/tmp/lepton-<context>-<config>-<time>.pftrace` | Needs `tracebox` on the host; performance, not errors |
| `bootchart` | Boots a throwaway container and dumps logcat plus bootchart | Boot-time analysis |
| `collect_logs` | Tars `lepton*` logs, `xrclient*`, and SteamVR's `console_log.txt` into `lepton-logs-<time>.tar.zst` with an `info.txt` | Written for SteamOS: it calls `pacman -Q`, so on Mint the version lines come out empty, but the logs are still collected |
| `ps` / `list_containers` | Lists live contexts with their adb port | Needed to find the context and adb port |
| `adb connect localhost:<port>` | Full adb into the container (`service.adb.tcp.port`) | `adb logcat` works the same as `lepton logcat`. On this machine the adb port forward goes through pasta, which is the part currently failing |

## Side-by-side

| | Android Translation Layer | Lepton |
|---|---|---|
| Where the app runs | Host process | Android 11 in a Podman container |
| Android log location | Process stdout/stderr | Container `logcat` buffers |
| Verbose switch | `ANDROID_LOG_TAGS=*:v`, `-X -verbose:jni` | Already unfiltered (`ro.logd.filter=disable`); no JNI trace flag (it is real ART, so `-verbose:jni` would need `dalvik.vm` properties) |
| Live stream | Read the pipes | `lepton logcat <context>` while running |
| After exit | Lost unless captured | `lepton-logcats/<context>/` on early exit or with `LEPTON_DUMP_LOGCAT` |
| Launcher log | None | `~/.local/share/lepton/logs/lepton-<context>.log`, always |
| Native debugging | gdb on the host process | gdbserver/lldb in the container, strace, Perfetto |

## How ApkManager could offer a Lepton Debug page

Not implemented; recorded here for a later decision.

1. Start the run as now (`run_lepton`), with `LEPTON_DUMP_LOGCAT=1` added to the
   launcher environment so a dump is always left behind.
2. Stream the launcher's stdout/stderr into the Debug page, the same as ATL.
   That covers setup failures like the current pasta error.
3. Once the launcher prints `Boot complete!`, spawn
   `lepton logcat steamlaunch-<id>` as a second subprocess, and feed its lines
   into the same page with the stream named `logcat`. Kill it when the run ends.
4. When the run ends, read `lepton-logcats/steamlaunch-<id>/logcat-crash.log`
   and `logcat-main.log`, if present, so a crash that happened between boot and
   the logcat attach isn't missed.
5. Reuse `atl_debug_error` with logcat's priority letter added: in
   `threadtime` format, lines with ` E ` or ` F ` in the priority column are
   errors. Logcat's `-v color` should be dropped (pass `-v threadtime`
   directly) so the page doesn't get ANSI escapes.
6. **Save JSON** works unchanged: the `apkManager`/`system` header,
   `~` home-path masking and the `YYYYMMDD.<app>.lepton.debug.HHMM.json`
   filename already apply to any runtime id.

Until the pasta port-forward error on Podman 4.9 is fixed, steps 3 and 4 have
nothing to show on this machine: Android never finishes booting, so the
launcher log from step 2 is the only useful output.

## Trying it by hand now

```bash
L=~/.local/share/Steam/compatibilitytools.d/lepton-x86_64/lepton

# Lepton's own log for every run
ls ~/.local/share/lepton/logs/
tail -f ~/.local/share/lepton/logs/lepton-steamlaunch-*.log

# While an app is running (started from ApkManager or Steam)
$L ps
$L logcat steamlaunch-<id>          # app only
$L logcat steamlaunch-<id> --full   # whole Android log
$L logcat steamlaunch-<id> '*:E'    # errors only

# Keep a logcat dump from every run, and trace the launcher itself.
# Set these in Steam's launch options (LEPTON_DUMP_LOGCAT=1 %command%) or in
# lepton.conf, since a bare waitforexitandrun lacks Steam's STEAM_COMPAT_* variables.
export LEPTON_DUMP_LOGCAT=1 LEPTON_DEBUG=1
ls ~/.local/share/lepton/logs/lepton-logcats/
```
