## 1. Where the information is

Android Translation Layer does not write a debug log file. A failed or half-started app reports on the terminal that launched it, on standard error, and the app's own `android.util.Log` calls come out through the same stream once the log tags are turned up.

Launching from a `.desktop` file, or from ApkManager's Run button, hides that stream. The Run button only shows a dialog when the process exits with an error, and that dialog keeps the last 400 characters after the final carriage return. A real diagnosis is a terminal session with the output saved to a file.

On this machine the command is:

```bash
android-translation-layer /path/to/app.apk
```

`command -v android-translation-layer` prints `/home/corey/.local/bin/android-translation-layer`.

The AppImage prints `failed to utilize FUSE during startup` and a percentage bar, then continues by extracting itself. That line is the AppImage runtime, not the Android app. Save both streams so the bar and the Java errors land in one file:

```bash
android-translation-layer /path/to/app.apk > ~/Downloads/atl-debug.log 2>&1
```

Leave the command running if a window appeared. The useful lines are often printed after the window is already up. Stop it with Ctrl+C when the failure has shown itself.

## 2. Turn the Android log up

Upstream's tip for the host `liblog` is:

```bash
ANDROID_LOG_TAGS=*:v android-translation-layer /path/to/app.apk
```

`*` means every tag. `v` means verbose and everything more severe. A tag other than `*` does not work with the host `liblog` ATL ships, so `ANDROID_LOG_TAGS=ActivityManager:v` stays quiet. The default level already prints the errors. `*:v` is the step when the window opens and then misbehaves, because the interesting lines are warnings the default filter drops.

This session is X11 (`XDG_SESSION_TYPE=x11`). ATL's README says GTK may pick GLX, which breaks ATL's EGL drawing, and the fix is:

```bash
GDK_DEBUG=gl-egl ANDROID_LOG_TAGS=*:v android-translation-layer /path/to/app.apk
```

ApkManager's Run button already sets `GDK_DEBUG=gl-egl` when the session is X11, and only if the variable is not already set. A blank window on X11 is this first, before treating it as a missing widget.

## 3. Ask ART for the class and JNI detail

`--help-all` on the installed launcher documents one switch that goes straight to ART:

```text
-X, --extra-jvm-option="OPTION"    pass an additional option directly to art (e.g -X "-verbose:jni")
```

The same flag can be repeated. The ones that explain a failed or partial start:

| Invocation | What it adds |
|------------|----------------|
| `-X "-verbose:class"` | Every class ART loads, and the point a class is missing |
| `-X "-verbose:jni"` | JNI registrations and lookups. The example in `--help-all` |
| `-X "-Xcheck:jni"` | ART checks JNI arguments and prints the bad call instead of crashing later |
| `-X "-Xnoimage-dex2oat" -X "-Xusejit:false"` | Upstream's workaround when ahead-of-time compiled code will not run. Forces the interpreter |

A first pass does not need `-verbose:class`. It is large. Use it when the process dies during startup and the ordinary stderr never names the class.

```bash
GDK_DEBUG=gl-egl ANDROID_LOG_TAGS=*:v \
  android-translation-layer /path/to/app.apk \
  -X "-verbose:class" -X "-verbose:jni" \
  > ~/Downloads/atl-debug.log 2>&1
```

`--sdk-int=N` is the short form of `-X "-DBuild.VERSION.SDK_INT=N"`. It changes the API level the app sees. It is a behavior switch, not a log switch. Use it only when the log says the app refused to start because of the SDK level.

## 4. How to read a startup failure

`doc/Architecture.md` gives the order the launcher walks. The log stops at the first step that throws:

1. The executable builds a classpath from `api-impl.jar` and the APK, then starts the Dalvik VM.
2. It loads `libtranslation_layer_main.so`.
3. It parses the manifest and creates the `Application`.
4. It creates the content providers from the manifest.
5. It calls `Application.onCreate`.
6. It creates the main activity (`-l` if given, otherwise the manifest's launcher activity) and calls `onCreate`.
7. After that, the process sits in the GTK main loop. Later failures are event-driven: a click, a network call, a drawn frame.

A process that exits before a window exists failed in steps 1–6. The text to keep is the Java exception at the end of the log, not the AppImage progress bar.

| Message | Meaning |
|---------|---------|
| `java.lang.NoClassDefFoundError` or "no such class" | ATL has no implementation of that Android class. QuickHelp's next step is a stub, or jadx when the missing name is one of the app's own classes that extends a missing Android class |
| `java.lang.NoSuchMethodError: No [static] method … in class L…` | The class exists, the method does not. The class name in the message is the one to stub |
| `java.lang.NoSuchMethodException` with no class name | The stack trace's call site has to be found in a jadx decompile. QuickHelp calls this out |
| `ExceptionInInitializerError` | A static initializer in the app, or in a stub, threw. The "Caused by" section is the real error |
| Window opens, controls missing or inert | The class was found and is still a stub. Verbose logs show which stub ran. This is the "partially runs" case upstream describes |
| Whole window blank or flickering on X11 | EGL versus GLX. `GDK_DEBUG=gl-egl` before looking for a missing class |
| Immediate native abort, or "cannot locate symbol" | The APK's `.so` asked for a function the bionic linker does not wrap. Section 5 |

`-l com.example.MainActivity` (dots, the form `--help-all` calls a fully qualified activity name) starts a specific activity when the manifest's default activity is the one that fails and another activity would get further.

## 5. Native libraries that do not load

ATL loads the APK's `.so` files with bionic_translation. That project's README documents three variables:

| Variable | Effect |
|----------|--------|
| `LINKER_PRINT_MISSING_SYMBOLS_AND_DIE` | After linking one `.so`, print every missing non-function symbol, then abort. Set to any non-empty value |
| `LINKER_DIE_AT_RUNTIME` | A missing function is wired to a stub that prints the function name and aborts when the app actually calls it, instead of failing at load |
| `BIONIC_LD_LIBRARY_PATH` | Colon-separated directories the bionic linker searches. Other libraries go to the platform linker |

```bash
LINKER_PRINT_MISSING_SYMBOLS_AND_DIE=1 \
  android-translation-layer /path/to/app.apk
```

`LINKER_DIE_AT_RUNTIME` is the one for a partial run: the window appears, then a later action aborts in native code. `LINKER_IGNORE_UNKNOWN_RELOCS` is a test switch. The bionic README says not to set it.

The extracted libraries for an APK land in that APK's data directory under `lib/`. A folder named only `armeabi-v7a` or `arm64-v8a`, with no `x86_64`, will not run on this machine. ATL does not translate ARM machine code.

`ATL_SKIP_NATIVES_EXTRACTION`, if set, stops ATL from extracting those `.so` files again. That matters after a library in the data directory was replaced: a normal launch puts the APK's copy back.

## 6. A Java debugger, when the log is not enough

`doc/Envs.md` says `JDWP_LISTEN=<port>` makes ART listen for `jdb` on that port:

```bash
JDWP_LISTEN=5005 android-translation-layer /path/to/app.apk
```

Connect from another terminal with `jdb -attach localhost:5005`. This is for stepping the app's Java, not for the missing-class case, which is already named in the exception.

The same document lists variables that change behavior rather than logging. They are useful once the log shows why a partial window is wrong:

| Variable | Effect |
|----------|--------|
| `ANDROID_APP_DATA_DIR` | Overrides the directory where the app's files are stored |
| `ATL_DISABLE_WINDOW_DECORATIONS` | No title bar. ATL does not subtract the title bar from the size it reports to the app |
| `ATL_FORCE_FULLSCREEN` | Fullscreen at start, for an app that cannot cope with a free-sized window |
| `ATL_UGLY_ENABLE_WEBVIEW` | If unset, WebView is a plain View. Set it when the missing piece is web content |
| `ATL_UGLY_ENABLE_LOCATION` | Allows the location APIs |
| `ATL_DIRECT_EGL` | SurfaceView is a Wayland subsurface or an X11 window instead of GtkGraphicsOffload |
| `RUN_FROM_BUILDDIR` | A source build looks for `api-impl.jar` and `libtranslation_layer.so` in the current directory. The AppImage does not need this |

`Envs.md`, as quoted in the February 2025 documentation update, describes the default data directory as `~/.local/android_translation_layer`. The copy on this machine writes `~/.local/share/android_translation_layer/<apk-file-name>_/`. Those folders hold the app's `files`, `shared_prefs`, `databases`, and `lib`. They are not a log. Their presence means startup got far enough to create private storage.

## 7. What ApkManager shows today

Run, on the Install APK window and beside Files and Properties, starts `android-translation-layer` with the APK path and, on X11, `GDK_DEBUG=gl-egl`. It does not set `ANDROID_LOG_TAGS`, and it does not pass `-X`. If the process exits with a failure, the dialog is the tail of stderr. The full sequence in section 3 is still a terminal command.

A desktop entry at `~/.local/share/applications/android-translation-layer.desktop` starts ATL with no terminal at all. Failures from that entry are invisible. Use the command in section 1.
