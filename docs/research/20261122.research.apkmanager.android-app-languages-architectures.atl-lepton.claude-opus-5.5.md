## 1. Short answer

On a phone or emulator, **almost every Android app is still an APK**: DEX bytecode for the managed side, optional native `.so` libraries under `lib/<abi>/`, and often a WebView or a bundled Chromium/Flutter/JS engine. The **language the developer wrote** mostly decides *which of those pieces exist* and *which Android APIs they call*. The **CPU ABI** of the `.so` files decides whether that machine can load them at all.

| Stack | What actually runs on Android | ATL (translation layer) | Lepton (full Android in a container) |
|-------|-------------------------------|-------------------------|--------------------------------------|
| **Java/Kotlin + x86_64** | ART runs DEX; optional `lib/x86_64/*.so` via bionic | Best ATL fit when APIs are implemented; natives must match host CPU | Runs like on a device; x86_64 image runs x86_64 libs natively |
| **Flutter** | Dart AOT in `libflutter.so` + thin Java shell | Hits engine JNI / NDK checks early; many missing classes | Full Android + matching ABI (or ARM translation on the x86 port) is far more realistic |
| **Cordova / Ionic** | Web UI in a system WebView + JS↔Java bridge | Needs a working WebView path (off by default in ATL; URL/bridge gaps) | WebView exists inside the image; closer to a phone |
| **React Native / Vue Native** | JS engine + native UI bridge | Same class of problem as Flutter: large native runtime + many APIs | Prefer Lepton / Waydroid-class runtimes |
| **Chromium-based** (Brave, Chrome, WebView-as-browser) | Huge native Chromium + JNI | Not a practical ATL target | Possible only as a full Android app with the right ABI |
| **ARM-only packages** | Load on ARM phones | **Cannot** load on x86_64 ATL (no instruction translator) | Official Lepton is ARM64; community x86 Lepton can translate ARM via `ndk_translation` |

**Yes — most real apps are a mix.** A "Kotlin app" often still ships C/C++ (NDK), and a "Flutter app" is Dart + Java/Kotlin + C++. Store labels name the *UI toolkit*, not a single language.

## 2. What every Android APK is made of

Ignore the marketing name for a moment. At install time Android cares about these layers:

```text
┌─────────────────────────────────────────────────────────┐
│  Your code (Kotlin, Dart, JS, C++, …)                   │
│       ↓ compiled / bundled into                         │
├─────────────────────────────────────────────────────────┤
│  classes*.dex          → ART (managed bytecode)         │
│  lib/<abi>/*.so        → linker + bionic (machine code) │
│  assets/, res/         → resources / bundled web / data │
│  AndroidManifest.xml   → components, features, ABI      │
└─────────────────────────────────────────────────────────┘
```

| Piece | Role on a real device |
|-------|------------------------|
| **DEX** | ART interprets or AOT-compiles it. Kotlin, Java, and much of the "glue" for Flutter/RN/Cordova end up here |
| **`lib/armeabi-v7a`, `arm64-v8a`, `x86`, `x86_64`** | CPU-specific native libraries. The package manager picks the folder that matches the device (or the app is rejected / fails at `System.loadLibrary`) |
| **System WebView / Chrome** | Cordova, Ionic, and many hybrids render HTML/CSS/JS here |
| **Play Services / DRM / camera / BLE** | Separate system services. Hybrids and big apps call them heavily |

**ATL** reimplements the framework in-process: ART from `art_standalone`, Android↔glibc via `bionic_translation`, UI as GTK 4. It does **not** emulate a second CPU. **Lepton** boots a real (minimal) Android 11 userspace in a rootless container, so DEX, binder, WebView, and package management behave much more like a phone. The community x86_64 Lepton port can run ARM code through **`ndk_translation`**; stock ATL cannot.

## 3. Java / Kotlin with x86_64 (or no native code)

### On Android

- Source is compiled to **DEX**. There is no JVM process; ART runs the bytecode.
- Kotlin is not a separate runtime on device: it becomes DEX plus the Kotlin stdlib in the APK.
- **x86_64** here means either:
  - **Pure managed:** no `lib/` folder (or only optional plugins), so the same APK runs on any ABI, or
  - **Managed + NDK:** `lib/x86_64/*.so` for JNI (SQLite, image codecs, game engines, libtorrent, …). On an x86_64 emulator or device those libraries load directly.

Examples from this machine's APKs: LibreTorrent (Kotlin/Java UI + `libtorrent4j` for x86_64), AntennaPod, OctoDroid.

### Under ATL

- DEX runs in `art_standalone`.
- x86_64 `.so` files load through `bionic_translation` on an x86_64 host.
- Success depends on whether ATL implements the **Java APIs** and any **bionic symbols** the `.so` needs (LibreTorrent failed on missing `__pwrite_chk`, not on Kotlin itself).
- This is the **sweet spot** for ATL: ordinary Views, sockets, files, light JNI.

### Under Lepton

- Behaves like Android 11: ART, binder, package manager, notifications.
- On **official Lepton (ARM64)**, you need an ARM APK (or a universal one with `arm64-v8a`).
- On **lepton-x86**, an x86_64-capable APK can run without translation; ARM libs can go through `ndk_translation`.

## 4. Flutter

### On Android

- UI and logic are mostly **Dart**, ahead-of-time compiled into **`libflutter.so`** (and often `libapp.so`).
- A thin **Java/Kotlin** `FlutterActivity` / `FlutterEngine` hosts the engine, handles plugins, and talks to Android APIs (lifecycle, accessibility, platform views, textures).
- Rendering is the engine's Skia/Impeller path via **EGL / Vulkan**, not a tree of Android `View` widgets (except platform views).

### Under ATL

- The host must load **`libflutter.so` for the host ABI** (x86_64 on this PC).
- The engine then **probes Android hard**: `dlopen("libandroid.so")`, JNI registration for classes like `android.media.Image`, accessibility types, code-cache directories, etc.
- Findings on ATL.edge: Neumorphic Calculator (`getCodeCacheDir`), dahliaOS Calculator (`libandroid` mapping missing from the AppImage), RustDesk (`Image` class). Fixing one blocker usually exposes the next.
- **Verdict:** possible in theory once many stubs and packaging pieces exist; today it is a **long cascade**, not a one-line fix.

### Under Lepton

- Flutter sees a real Android userspace (WebView, libandroid, accessibility services as the image provides them).
- Still need the right ABI (or ARM translation on the x86 port).
- **Verdict:** much closer to "install the F-Droid APK and run," subject to Lepton's own GPU / window limits.

## 5. Cordova

### On Android

- The app is mostly **HTML/CSS/JS** under `assets/www/`.
- **Cordova's Java layer** creates a **WebView**, loads `file:///android_asset/www/index.html`, and exposes device APIs to JavaScript through a bridge (`_cordovaNative` / `cordova.exec`).
- Plugins are small Java classes plus optional native code.

### Under ATL

- ATL's WebView is **gated** (`ATL_UGLY_ENABLE_WEBVIEW`) and backed by **WebKitGTK**, not Android's Chromium WebView.
- Asset URLs are rewritten to `android-asset://…` for WebKit; Cordova's allow-list still expects `file:///android_asset/…`, so navigation can be blocked (SureSupply finding).
- Even with the page loading, **`javascript:` URLs** and **`addJavascriptInterface`** are incomplete, so plugins often stay dead.
- **Verdict:** needs a deliberate WebView + bridge project in ATL; not "just enable a flag."

### Under Lepton

- System WebView (or the image's WebView provider) exists inside Android.
- Cordova behaves much more like on a phone, including plugins that only need ordinary Android APIs.
- **Verdict:** preferred runtime for Cordova apps on Linux today.

---

## 6. Ionic

### On Android

- Ionic is a **UI framework** (web components, Angular/React/Vue) that ships as a web app.
- On Android it almost always sits on **Capacitor** (current) or **Cordova** (older): same WebView shell pattern as Cordova, with `assets/public/` (Capacitor) or `assets/www/` (Cordova).
- So "Ionic" in an APK means **web UI + native bridge**, not a separate VM.

### Under ATL / Lepton

- Same as Cordova/Capacitor: ATL needs WebView enablement, correct asset URLs, and a JS bridge; LocalCrop (Capacitor) showed an empty window with WebView off and no `shouldInterceptRequest`.
- Lepton again looks like a normal Android WebView host.

Ionic does **not** change the ABI story: any Cordova/Capacitor plugin `.so` still needs `lib/x86_64` on ATL x86_64.

## 7. React Native

### On Android

- **JavaScript** (Hermes or JSC) runs in-process.
- UI is **not** a WebView by default: a bridge (or JSI / Fabric) maps React components to real **Android Views**.
- Large native libraries (`libreactnativejni.so`, Hermes, etc.) ship per ABI.
- Heavy use of Android framework APIs from both Java and C++.

### Under ATL

- Requires loading the RN native stack on the host ABI **and** a very wide set of View / lifecycle / networking APIs.
- Same failure mode family as Flutter: early native or missing-class crashes, then a long tail of stubs.
- **Verdict:** poor ATL candidate until ATL's framework coverage is much deeper.

### Under Lepton

- Designed for "unmodified Android apps"; RN is exactly that once the ABI matches.
- **Verdict:** use Lepton (or Waydroid), not ATL, for React Native.

---

## 8. Vue Native

### On Android

- **Vue Native** was a Vue syntax layer that compiled toward **React Native** primitives. The project was **abandoned** (archived / unmaintained years ago).
- Apps still in the wild are effectively **React Native apps** with a Vue-like authoring experience at build time.
- There is no separate "Vue Native VM" on the device.

### Under ATL / Lepton

- Treat them as **React Native**: ATL is a hard path; Lepton (or Waydroid) is the realistic one.
- New projects would use **Ionic Vue + Capacitor**, **NativeScript-Vue**, or **Quasar** instead — those fall under the Cordova/Capacitor or native-bridge categories above, not under Vue Native.

## 9. Chromium (browsers and Chromium-powered shells)

### On Android

- **Chrome / Brave / Chromium** are enormous multi-process native programs: C++ Chromium, JNI, sandbox, GPU process, plus a relatively small Java UI layer.
- Many "apps" embed Chromium via **Custom Tabs**, **Trusted Web Activity**, or a private WebView; full browsers ship their own `libchrome` / `libmonochrome` / similar under `lib/<abi>/`.
- They expect split APKs / feature modules (`ApplicationInfo.splitNames`), Play updates, and often Widevine / account stacks.

### Under ATL

- Brave on ATL.edge died early on a missing `splitNames` field; past that, Chromium's native and sandbox requirements are far outside ATL's GTK-shaped process model.
- **Verdict:** not a credible ATL goal. Use a desktop browser on the host.

### Under Lepton

- A full Chromium APK can run *as an Android app* if the image has the ABI (or translation) and enough services.
- Still heavy (RAM, GPU, Play/DRM). Often pointless next to Firefox/Chrome on Linux.

## 10. ARM-only packages

### On Android

- "ARM-only" means the APK's `lib/` tree has **`armeabi-v7a` and/or `arm64-v8a` only** — no `x86` / `x86_64`.
- On an ARM phone that is normal. On an **x86_64 emulator without translation**, `System.loadLibrary` fails.
- Play and some stores serve **split APKs by ABI**; a file named `…universal…` can still be ARM-only (PUBG MOBILE on this machine).

### Under ATL

- ATL runs native code **as host machine code**. On an x86_64 PC it only opens `lib/x86_64/` (and related).
- **No** `libhoudini` / `libndk_translation` in ATL. ARM-only APKs (TikTok `.arm64.apk`, PUBG without x86_64) **cannot** be fixed by stubbing Java APIs.
- ApkManager can only warn before launch.

### Under Lepton

- **Official Steam Lepton:** ARM64 host and ARM64 image — ARM-only APKs are the *expected* case.
- **Community lepton-x86:** can run ARM binaries through **`ndk_translation`** (with the port's GPU and feature limits).
- **Verdict:** ARM-only store apps belong on Lepton (ARM machine or x86 port with translation) or Waydroid with an ARM translator — not on ATL x86_64.

## 11. Side-by-side comparison

| Concern | Java/Kotlin x86_64 | Flutter | Cordova / Ionic | React Native / Vue Native | Chromium | ARM-only |
|---------|--------------------|---------|-----------------|---------------------------|----------|----------|
| Primary code on device | DEX (+ optional JNI) | Dart AOT `.so` + DEX glue | JS in WebView + DEX bridge | JS engine + DEX + many `.so` | C++ Chromium + DEX | Same as app type, wrong ABI for x86 |
| UI toolkit | Android Views / Compose | Flutter engine | HTML | RN native Views | Chromium UI | — |
| ATL outlook | **Best** | Hard cascade | WebView project | Hard cascade | Unrealistic | **Impossible** on x86_64 |
| Lepton outlook | Good | Good if ABI OK | Good | Good | Heavy but "real Android" | **Natural** on ARM Lepton; translated on x86 port |

## 12. Are there applications written in a mix of languages?

**Yes. Mixing is the default, not the exception.**

| Mix | What you see in the APK | Examples |
|-----|-------------------------|----------|
| **Kotlin/Java + C/C++ (NDK)** | `classes.dex` + `lib/<abi>/*.so` | LibreTorrent (UI + libtorrent), games, image codecs, Termux (Java UI + many ELF binaries) |
| **Dart + Kotlin/Java + C++** | `libflutter.so`, `libapp.so`, Flutter embedding classes | Neumorphic Calculator, RustDesk, dahliaOS Calculator |
| **JS + Java + optional NDK** | `assets/www` or `assets/public`, Cordova/Capacitor classes, sometimes plugin `.so` | SureSupply (Cordova), LocalCrop (Capacitor / Ionic-style) |
| **JS + Java + C++ (RN)** | Hermes/JSC libs + RN JNI + DEX | Typical React Native release APK |
| **Java UI + bundled Chromium** | Huge `lib/*/libchrome*.so` (or similar) + DEX | Brave, Chrome |
| **Multiple UI stacks in one product** | e.g. native settings + WebView content, or Flutter screen inside a native app (`FlutterFragment`) | Common in large commercial apps |
| **Build-time mix only** | Kotlin calling Java libraries; Vue Native compiling to RN; Ionic TS compiling to web assets | The device never sees Vue/TS — only DEX, JS bundles, and `.so` files |

How to **detect** a mix when triageing for ApkManager:

```bash
unzip -l app.apk 'lib/*' 'assets/flutter_assets/*' 'assets/www/*' 'assets/public/*' \
  'classes*.dex' 2>/dev/null | head
# Flutter:      lib/*/libflutter.so + assets/flutter_assets/
# Cordova:      assets/www/ + org/apache/cordova in dex (or smali)
# Capacitor:    assets/public/ + com/getcapacitor
# Chromium:     enormous lib/*/lib*chrome* or monochrome libs
# RN:           lib/*/libreactnative*.so / libhermes.so
# ABI:          which of arm64-v8a, armeabi-v7a, x86, x86_64 appear under lib/
```

**Implication for ATL vs Lepton:** when people say "it's a Kotlin app," still check `lib/`. A single missing bionic symbol in a JNI library (LibreTorrent) or a single ARM-only folder (TikTok) dominates runtime choice more than the UI language does.

## 13. Practical guidance for ApkManager

1. **Classify the APK** (DEX-only / JNI, Flutter, Cordova-Capacitor, RN, Chromium, ABI) before choosing a runtime.
2. **ATL first** only for Java/Kotlin (and similar) apps with **x86_64 or no native libs**, modest API use.
3. **Lepton (or Waydroid)** for Flutter, RN, Cordova/Ionic that need a real WebView, and **any ARM-only** package on an x86 host that has translation.
4. **Do not** treat Vue Native as its own runtime — fold it into React Native.
5. Expect **mixed** APKs; the failure you see (missing Java method vs missing `.so` symbol vs wrong ABI vs WebView) tells you which layer broke, not which language the README advertised.
