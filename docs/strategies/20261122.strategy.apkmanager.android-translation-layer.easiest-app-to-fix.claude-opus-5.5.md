## 1. Verdict

**Among the apps in `00.references/errors`, LibreTorrent is the easiest to get usefully working by fixing ATL.**

The crash is one missing bionic symbol (`__pwrite_chk`) in `libtorrent4j.so`. The suggested fix is a few small C wrappers in **bionic_translation**, not a new Android API surface. After that, the finding expects the main screen to appear, and basic torrenting has a realistic chance because it needs ordinary sockets and file I/O, which ATL already passes to the host.

No other tested app combines a **small, localized fix** with a **realistic chance of useful behaviour** after that fix. Several are easier to *patch past the first crash*, but then hit a wall (Flutter class cascade, WebView bridge, Bluetooth, DRM, wrong CPU architecture).

If LibreTorrent still stalls after `__pwrite_chk`, the next best bets are **not** the Flutter / Cordova / ARM-only apps from this set. Prefer ATL's own demos (Gravity Defied, GLES samples) or F-Droid Java/Kotlin apps with an **x86_64** (or no-native) build: **OctoDroid** (`com.gh4a`, already on disk here; ATL already special-cases it) and simple Material FOSS tools. Avoid Flutter, Capacitor/Cordova, Chromium browsers, streaming DRM, and BLE-heavy apps until those layers exist in ATL.

## 2. How the ranking was done

"Easiest to get **working**" means all three, not only "easiest first patch":

1. **Fix size** — lines of code, and how many ATL / art_standalone / bionic pieces are involved.
2. **Likelihood the app is usable after that fix** — UI up, and the app's main job can run on what ATL already provides (GTK widgets, EGL, host sockets, host files).
3. **ABI** — the APK must include **x86_64** (or no native libraries). ARM-only packages cannot be fixed in ATL on this PC.

ApkManager-only bugs (the "Dismissed by user" exports, `GDK_DEBUG=gl-egl`) are out of scope: they are not ATL app failures.

### Why LibreTorrent wins over VLC

VLC's first two patches are as small as LibreTorrent's, and may even be smaller. The difference is **what "working" means**:

- LibreTorrent's core job (download and write torrent data) maps onto **host sockets and files**, which ATL already has.
- VLC's core job is **decode and present video**, which depends on Android media surfaces and codecs. Getting past Leanback does not mean playback works.

So LibreTorrent is the better **first proof that a real user app works under ATL.edge**, not only that ATL fails later.

## 4. Recommended first fix (LibreTorrent)

Follow the LibreTorrent finding:

1. In **bionic_translation**, add `bionic___pwrite_chk` / `bionic___pwrite64_chk` (and ideally `__pread_chk` / `__pread64_chk`) beside the existing `bionic___write_chk` pattern, and register them in the symbol map.
2. Rebuild ATL.edge (or rebuild only bionic_translation and restage the AppImage) so `libtorrent4j.so` can `dlopen`.
3. Rerun `org.proninyaroslav.libretorrent.from.F-Droid.x86_64.apk` under ApkManager debug capture.
4. If a new missing symbol or API appears, fix the next **localized** gap the same way. Stop and reassess if the failure moves into WorkManager, notifications, or SAF in a way that blocks all downloads.

Success criteria for this strategy: the library loads, the main activity stays up, and at least one torrent can be added and written to disk under ATL's data directory.

## 5. If none of these become usable: what to try from stores / repos

### 5.1 Prefer apps ATL already demonstrates

From [atl_test_apks](https://gitlab.com/android_translation_layer/atl_test_apks) and the ATL README screenshots:

| APK / app | Why |
|-----------|-----|
| **Gravity Defied** (`org.happysanta.gd_29.apk`) | Documented run example; GLES game ATL authors ship |
| **gles3jni**, **glmark2**, **Endless Tunnel** | NDK / GLES samples with known command lines in `NOTES.md` |
| Older casual games (Angry Birds–style, Worms) shown in ATL screenshots | Prove EGL / input; not in ApkManager's error set |

These are the lowest-risk way to see a **working** ATL window on this machine before chasing store apps.

### 5.2 F-Droid / OpenAPK / Aptoide selection rules

When picking a new APK from ApkManager's stores:

| Prefer | Avoid |
|--------|--------|
| **x86_64** or **no `lib/`** at all | `arm64-v8a` / `armeabi-v7a` only (PUBG, TikTok pattern) |
| Pure **Java/Kotlin** UI (Material, AppCompat) | **Flutter** (`libflutter.so`), **React Native**, **Capacitor**, **Cordova** |
| Offline or plain HTTP(S) tools | DRM streaming, Play Integrity, heavy Play Services |
| Single-APK FOSS from **F-Droid** | Multi-split Chromium browsers (Brave) |
| Apps whose native code is one focused library (libtorrent, sqlite) | Full media engines and browsers |

### 5.3 Strong candidates already on this machine (not in the error set)

| APK | Why try it next |
|-----|-----------------|
| **OctoDroid** `com.gh4a.from.F-Droid.universal.apk` | Has x86_64. ATL's `WebView.addJavascriptInterface` already contains an OctoDroid-specific hack, which strongly suggests the authors care about this app. GitHub client; mostly network + WebView for Markdown |
| **AntennaPod** `de.danoeh.antennapod.from.F-Droid.universal.apk` | Has x86_64. Classic Java podcast client. May need audio / MediaSession work, but closer to "ordinary Android app" than Flutter calculators |

### 5.4 Store search ideas (not yet downloaded)

Good F-Droid search targets for ATL:

- Classic **Material calculators** that are **not** Flutter (check the APK for absence of `libflutter.so`).
- **Markor**, **Simple Calendar** / **Simple Gallery**-style "Simple Mobile Tools" apps (Kotlin, little or no native code).
- **NewPipe** / **PipePipe** only after media paths are known good (harder than LibreTorrent).
- Small **SDL2** or **libGDX** games that ship an **x86_64** `.so` (ATL already has SDL-related samples).

Skip for now: anything BLE mesh, anything Capacitor (`assets/public` + `com.getcapacitor`), Cordova (`assets/www` + `org.apache.cordova`), and any "universal" APK that is actually ARM-only when you list `lib/`.

## 6. Suggested order of work

1. **Ship the LibreTorrent `__pwrite_chk` fix** in bionic_translation and rebuild ATL.edge.
2. **Capture a new debug export** for LibreTorrent. Treat a lasting main activity as success for this strategy.
3. In parallel or next: **fix the AppImage `bionic_translation` cfg packaging** (dahliaOS finding). That helps every Flutter / NDK app, even though Flutter is still a longer path.
4. **Add the VLC touchscreen + `setSoundEffectsEnabled` stubs** as cheap shared hygiene (helps many non-VLC apps too), without treating VLC playback as the success metric.
5. If LibreTorrent is not enough of a win, run **OctoDroid** and ATL's **Gravity Defied** test APK under ApkManager and write findings the same way.

---

## 7. What this strategy is not

- It does not claim LibreTorrent will be feature-complete (notifications, background service, SAF folders may still be incomplete).
- It does not recommend chasing Brave, TikTok, PUBG, Disney+, Termux, or Wine-for-Android as ATL learning targets on this x86_64 host.
- It does not replace Waydroid/Lepton for apps that need a full Android stack (Play Services, BLE, DRM).
